# 《福瑞快打》需求方案（V1.37 · 与当前实现同步）

> **V1.37 双人对战内核（第一批：能一起打 + 各自选卡）**：V1.36 的房间已经能建房 / 邀请 / 加入，本版把**对局同步的第一批**落地。
> ① **玩家槽位** —— `squad / soldiers / squadHp / stats / weapons / summons / pet / skills / pickCount / routePicks / appliedIds / dmgBonus / dmgBase` 这批全局变量改成「**当前生效玩家**」的镜像（`players[]` + `switchTo(p)` / `withCtx(p, fn)` / `captureCtx` / `loadCtx`），现有 40 多个战斗函数**一行没改**；**单人局的切换是空操作**，零行为变化。
> ② **房主权威 + 客机回放** —— 房主跑完整模拟并以约 **18Hz** 广播世界快照（Supabase Realtime 的 **public broadcast** 频道 `room:<房间码>`，手写 Phoenix 裸 WebSocket，实测不走 `realtime.messages` 策略所以**零 DB 迁移**）；**客机不跑 `update()`**，只上行移动意图、按快照回放 `render()`。
> ③ **跨玩家判定** —— 敌人索敌与半径类范围伤害（自爆怪爆炸、首领冲锋撞击与震波、首王砸落、精英爆炸、敌弹命中、敌人与小队站位分离）全部**跨两名玩家**，半径用**各人自己的** `bodyR()`；扣血按 `soldier.owner` 记账，全灭判据改成「两人都不剩小兵」。
> ④ **升级 · 各自选卡** —— 等级与经验**共享**，但**候选各抽各的**；世界在**所有人都选完之前保持冻结**，客机的选择由房主在客机的上下文里落地。
> ⑤ **收场链路** —— 房主打完一局（阵亡 / 通关）会广播结果，**客机也能看到结算页**（数字与阵亡原因来自房主，金币与成绩只在房主那侧结算）；中途退出统一「通知对方 + 回大厅」；**通道的存活周期是「在房间里」而不是「这一局」**，所以一局结束后房主在房间里重新开局即可再打。
> ⑥ **打击反馈同步** —— 伤害数字 / 浮动文字 / 屏幕抖动随快照节拍单独发一条 `fx`（纯表现、可丢），客机打怪不再是「怪默默掉血」。
> ⑦ **把几个「其实该按玩家分」的全局补进槽位** —— 雷电那条线的硬性触发间隔（`lightningCdT` / `lightningPending`）、受伤来源统计（`hurtBy` / `lastHurt`）、宠物熟练度（`petRunExp`）：此前双人下客机打出的雷会把房主的雷卡在冷却里、两人的受伤混进同一份阵亡原因。
> ⑧ **修复**：客机此前从未建立过连接（输入全发不出去）、`netConnect` 没等 `phx_join` 确认就 resolve（开局广播被静默丢弃）、客机打完一局只会停在冻结的战场上（收不到任何收场消息）、开局消息过大（改为只发种子）、开局后好友面板盖住战场。
> ⚠️ **这一批只做到「能一起打」**：快照插值（只有固定系数平滑）/ 顿帧与音效（客机听不到打击音）/ 断线重连 / 双人难度放大 / 合作榜**仍未做**；结算页虽能两边显示，但用的是**房主那一份数据**。见第 12 节。详见 [2.7](#27-合作对局v137)。

> **V1.36 合作房间（第一批：房间系统）**：好友面板底部的「合作房间」从**纯 UI 占位**升级成**能真的用**的一小套 —— **生成 6 位房间码**（字母表去掉 `I / O / 0 / 1`，念给好友听不会认错）· **复制邀请链接**（`?room=<房间码>`，对方点开自动打开好友面板并填好房间码）· **输入房间码加入** · **房间里两个席位**（头像 + 名字 + 房主 / 已准备，空席位显示「等待好友加入…」）· **准备 / 离开** · **在好友列表里直接「邀请进房」**（房间还空着时才显示）· **收到的邀请**带「加入 / 忽略」，并计入首页红点。
> 服务端新增 `rooms` 与 `room_invites` 两张表（`supabase/migrations/0007_rooms.sql`）与 `api/rooms.js`（本地 `server.js` 等价实现落盘 `data/rooms.json`）；沿用「**身份取自令牌、RLS 零策略、不进 Realtime、轮询兜底**」这套既有做法，**3 秒轮询**。
> ⚠️ **V1.36 时对局同步尚未实现**（双方都点「准备」只是大厅状态位）；**V1.37 已补上「能一起打」的内核**，见 [2.7](#27-合作对局v137)。详见 [2.6](#26-合作房间v136)。

> **V1.33 四线「专精」+ 牛来造型校正**：① **火焰 / 雷电 / 飞剑 / 镰刀各加一条三段「专精」卡**，与「质变链」分工明确 —— 质变链是概率触发的机制，专精是**确定的数值成长**，而且补的是**固定伤害**（全游戏第一处「固定值直接加到基础值上」）：火焰 **+3/+6/+12** 固定火焰伤害与点燃 **+0.3/+0.8/+1.5s**；闪电让**落雷变成范围伤害**（半径 **90/130/180**、范围伤害为本次雷击的 **30%/45%/60%**）并 **+10%/+20%/+35%** 闪电伤害；飞剑与镰刀各 **+2/+5/+9** 固定伤害与**命中冷却 -8%/-15%/-25%**。**卡面显示的是「选完这次之后的累计值」**。② **「牛来」按原片校正 3 处**：角从奶油色改成**深棕色**、口鼻改成**肉色**、眼睛改成**纯色方形瞳孔（去掉高光）**。详见 6. 与 2.。

> **V1.32 第二阶段架构：双模式 + 存档版本与迁移 + 三条随机流 + 显式状态机**：① **两种基础模式** —— **标准模式**（固定 20 波，打完第 20 波即通关结算，一局约 15~20 分钟）与**无尽模式**（**标准模式通关后开放**，没有波数上限）；通关会解锁无尽模式，成绩按实际打完的波数上报。② **存档加 `schemaVersion` 与迁移流程** —— 读档统一走 `migrateMeta()`（校验 → 逐步迁移 → 补齐字段 → 再校验并盖版本号），**没有版本号的老存档按 v1 处理并自动升级**；配套**存档校验**（宽松 / 严格两档）、**坏档备份**（`__backup` / `__broken`）、**写入失败回滚**（临时键 + 回读校验的原子写，失败保持旧档不变）与开发者面板的「恢复上次备份」。③ **`Math.random()` 拆成世界 / 战斗 / 表现三条随机流**（`rngWorld` / `rngCombat` / `rngFx`，mulberry32），**种子与三条流的取用位置写进 `meta.run`**，同一种子可复现同一张地图与同一套战斗判定。④ **显式状态机** —— 全部状态与「占用哪个遮罩 / 世界是否推进 / 局内按钮是否显示」写在一张表里，切换统一走 `setState()`（含预留的 `merchant`）。⑤ **模块边界** —— 在 `js/game.js` 内先立**数据 / 逻辑 / 渲染 / UI** 四层清单与可验证不变量（渲染层只读世界、不消耗 world / combat 随机流），暂不拆文件。⑥ **需求 8 落地** —— 宠物吃「自己那条元素线」的**独占增伤**（雷电虫走闪电线，折半 `ELE_SHARE = 0.5` + 封顶 `+50%`；冰霜领域吃「霜冻附魔」，减速时长取 max）；同轮还把**牛来**按 2026 年那部同名电影的原样重做成**低模**、并重做了四把枪的模型。详见第 2 节、11 节与 2.4、4.4。

## 2.3 排行榜（局外 · V1.6）

入口为**主菜单 → 排行榜**（主页底部导航第 4 项）。榜单按账号的**最久波次**倒序排列，每位玩家只占一行，当前账号高亮。

**成绩来源与写入**
- 阵亡结算（`gameOver`）时上报**本局波次与本局时长**（`gameTime`）；开发者模式改了最佳波次也一并上报（会声明足够的对局时长以通过校验）。
- 写入走 `POST /api/leaderboard`，需要**会话令牌**，身份取自令牌而不是请求体，因此无法替别人上报成绩。
- 服务端调用数据库函数 `submit_score`：**一条语句内取较大值**，波次比库里小则整行不变（连 `updated_at` 都不动），多人同时提交不会互相覆盖；同一条语句里还做合理性校验：
  - 波次上限 5000、单局时长上限 12 小时；
  - `波次 ≤ 时长 ÷ 2 + 30`（一局最多每 2 秒推进一步，另给 30 波容错），超出直接拒绝并返回 400。

> **校验的边界**：本游戏是纯前端客户端，服务端只能验证上报的数字自不自洽，**无法证明这一局真的打过**。这道校验挡的是「随手 POST 一个 9999」，挡不住刻意伪造时长的提交；要真正防住需要服务端复盘对局（见第 13 节）。

**读取与实时更新（三级保障）**

| 层级 | 机制 | 表现 |
|---|---|---|
| 首屏快照 | `GET /api/leaderboard?limit=50` | 打开榜单立刻有数据 |
| 实时推送 | 前端用原生 `WebSocket` 直连 Supabase Realtime，订阅 `scores` 表 `postgres_changes` | 有人破纪录 → 秒级刷新（订阅成功显示「实时同步中」） |
| 轮询兜底 | 订阅不可用 / 断开 / 8 秒内无应答时，每 8 秒拉一次接口 | 显示「每 8 秒刷新一次」，榜单不会停在旧数据 |

- 实时通道未使用 `supabase-js` SDK，直接走 Realtime 的 Phoenix 协议（`phx_join` + `postgres_changes` + 25 秒心跳），保持项目「零运行时第三方依赖」。
- 连接信息（`wss://<ref>.supabase.co/realtime/v1/websocket` + publishable key）由后端随 `GET /api/leaderboard` 下发；未配置 publishable key 时下发 `null`，前端自动只走轮询。
- 离开排行榜页或回主页即断开订阅与轮询。
- 玩家名来自其他账号，渲染一律走 `textContent` 而非拼 HTML，避免 XSS。

**前三名装饰与主题适配（V1.8）**

- 第 1 名玩家名前渲染一枚内联 SVG 皇冠（`boardCrown()` / 常量 `CROWN_SVG`），该行同时用金色描边 + 左起渐变高亮。
- 名次配色分三档：第 2 名（银）`color-mix(in srgb, #c3cfd4 30%, var(--ink))`；第 3 名（铜）`color-mix(in srgb, #d79a63 30%, var(--ink))`；第 1 名与第 4 名起为金 `--gold`，其中**榜首再额外往 `--ink` 收 12%**（`color-mix(in srgb, var(--gold) 88%, var(--ink))`）。
- 皇冠填充取 `--gold`，跟随五种界面主题变色（如霓虹街机为粉紫）；用内联 SVG 而不是 emoji，避免各平台字体差异；描边沿用 10.5 的深色粗描边。
- 行内布局：`.board-user` 是 flex 容器，玩家名在 `.board-name` 中。皇冠 `flex: none` 固定宽度，名字过长时只截断名字本身，皇冠不会被一起压掉。
- **行底与文字都跟随主题**：行底 `color-mix(in srgb, var(--surface) 92%, transparent)`、玩家名 `var(--ink)`、选中行 `color-mix(in srgb, var(--mint) 10%, var(--surface))`，与 `.tab` / `.card` 同一范式。
- **银与铜为什么不能写死**：两者都是浅色，固定取值后落在暖纸手绘这类浅底主题上对比度只剩 1.36:1 / 2.06:1。改为按 `--ink` 方向收 30% 后，深色主题下偏亮、浅色主题下偏暗，五个主题实测均 ≥ 4.91:1。
- **榜首为什么比第 4 名多收一点**：冠军数字落在榜首行金色渐变的左端，局部底色被金色抬亮，纯 `--gold` 在暖纸手绘下只有 4.40:1；收 12% 后升到 4.72:1。第 4 名起落在纯行底上，不需要这一步。四个名次档在五个主题下均 ≥ 4.5:1（详见更新日志 v1.8 的验证一节）。
- **窄舞台的紧凑布局**：两侧列宽抽成 `--board-rank-w` / `--board-wave-w`（默认 34px / 72px）。`#menu` 上设了 `container-type: inline-size`，当它的宽度 ≤ 280px 时切紧凑分支：列宽收紧为 22px / 46px、`gap` 8px → 6px、行内边距 11px 12px → 9px、表头字号 11px → 10px，并把 `.board-name` 从 `nowrap` 改成 `white-space: normal` + `overflow-wrap: anywhere`——超长名字改为**完整换行**显示，而不是被截成一小截。
- 列宽之所以抽成变量，是因为表头 `.board-head` 与数据行 `.board-row` 是两个独立的 grid，只有共用同一组列宽才能保持对齐。
- 之所以用**容器查询而不是媒体查询**：舞台宽度由「显示方向」设置与视口共同决定（竖屏 `--arw .5625`，横屏另算，见 2. 主菜单的显示方向项），媒体查询判不出实际舞台宽度。
- 阈值取 280px 的依据：正常布局下玩家名列宽为「行宽 − 146px」，280px 舞台时只剩约 101px（够放约 7 个汉字），再窄就该让位给换行；280px 以上正常布局仍够用，不必改变 320×568 等验收尺寸下的观感。

**数据表**：`public.scores`（`username` 主键、`best_wave`、`updated_at`）。RLS 开启，只给 `anon` / `authenticated` 开放 `SELECT`（Realtime 订阅与榜单读取所必需），写权限全部收回，提交只能经服务端密钥。

## 2.4 账号与存档（V1.6）

**密码只存哈希**
- 存储格式 `pbkdf2$sha256$<迭代次数>$<盐base64>$<哈希base64>`，迭代 120000、每账号 16 字节随机盐；服务端（Node `crypto`）与本地通道（Web Crypto）格式一致。
- 老账号（`users.password` 明文列）**首次登录成功时原地升级**：写入 `password_hash` 并把明文列置空，用户无感。
- 任何接口都不返回密码或哈希；`GET /api/users?username=` 只回 `username` 与 `meta`。

**接口契约**（`api/users.js` 与本地 `server.js` 完全一致；标注「需令牌」的都要 `Authorization: Bearer <token>`）

| 方法与路径 | 用途 |
|---|---|
| `GET /api/users` | 探活，前端据此判断走在线接口还是退回本地存储（唯一无需令牌的读接口） |
| `GET /api/users?username=<name>` | 取自己的账号（刷新后恢复登录态），需令牌；读别人的返回 403 |
| `POST /api/users` `{action:'login'}` | 服务端校验密码，成功返回 `{ user, token }` |
| `POST /api/users` `{user, createOnly:true}` | 注册，无需令牌（靠账号名判重，重名返回 409），返回 `{ token }` |
| `POST /api/users` `{user}` | 改密，需令牌；只改密码两列，**不碰存档**，返回新令牌 |
| `PATCH /api/users` `{username, meta, avatar}` | 只更新存档，需令牌，且用户名必须与自己一致；**V1.34 起附带 `avatar` 公开副本**（见 2.5） |
| `DELETE /api/users?username=<name>` | 删除账号，需令牌，只能删自己；**V1.34 起一并清理该账号的 `friendships` 关系行**，**V1.35 起再补上两个方向的 `messages` 私聊行**（否则会留下指向已删账号的孤儿消息）。`server.js` 本地实现同样清 `data/friendships.json` 与 `data/messages.json` |

**会话令牌（无状态签名串）**
- 格式 `<payloadBase64Url>.<HMAC-SHA256Base64Url>`，payload 为 `{ u: 用户名, pv: 密码版本, exp: 过期时间戳 }`，有效期 30 天；服务端不需要额外建表。
- `pv` 取当前密码哈希的摘要前 16 位，**改密后旧令牌立即失效**；令牌缺失/过期/签名不符一律 401。
- 签名密钥取 `SESSION_SECRET` 环境变量，未配置时退化为由服务密钥派生（同样只在服务端）。
- 登录与注册时随响应下发，前端存 `localStorage.fury_token`，退出登录即清除。
- 令牌只证明「请求方登录过这个账号」，**不是**服务端权威成绩记录的替代品。

**接口改造的关键点**：注册用 `createOnly` 走数据库主键的 `ignore-duplicates`，只能新建、不能覆盖；改密（`POST` 不带 `createOnly`）只动密码两列，避免旧客户端拿陈旧存档覆盖新进度；原先的「整表覆盖」写入口已删除。

**存档同步与本地兜底**
- `saveMeta()` 先写本机镜像（`localStorage.fury_meta_<账号>`，不依赖网络），再同步到后端；失败按 0.8s / 1.6s 退避重试两次。
- 仍失败时首页显示「存档暂未同步到云端，已存在本机，联网后自动重试」。
- 每次存档写入 `meta.savedAt` 时间戳；下次登录时若本机镜像比云端新，会询问是否用本机这份覆盖云端（覆盖的是**返回首页保存的那份进度快照**这类容易丢的数据）。
- `meta.savedAt` 也让「返回主菜单保留本局进度」在线上可靠成立：快照随 `meta.run` 一起进 `PATCH`，刷新后从服务端取回。

**三通道**：Electron IPC → `/api/users` → `localStorage`。本地通道自己算哈希后再落盘；在线通道明文口令只在 HTTPS 上传输一次，哈希由服务端完成。

> 仍存在的边界：令牌签发前已经在浏览器里的旧登录态会失效一次，**升级后所有人需要重新登录一遍**。另外客户端仍是成绩的唯一来源，见 2.3 的校验边界说明与第 12 节。

## 2.5 好友与头像（V1.34；V1.35 换了入口）

> 本条是**真实好友关系**（存服务端），不是本地假数据；**合作房间**见 2.6（V1.36 起已是能真的建房 / 邀请 / 加入的房间系统，但**双人对局的同步内核尚未实现**）。

### 入口与界面（V1.35 改）

- **入口**：主页右上角，**设置齿轮正下方**竖排的一个好友图标按钮（`#btn-friends`），右侧带**未处理申请的红点徽章**（数量为 0 时隐藏）。**V1.34 的主页右侧常驻好友栏（`#home-side`）已取消** —— 首页其余 UI 一律不动，也不再给自己留 `padding-right` 通道。
- **界面**（`#friends`）：点入口直接进入好友界面，**它本身就是一个独立面板**，内容自上而下是：我的卡片（头像 + 用户名 + 「更换头像」）· **加好友输入框 + 添加按钮**（就在这个界面里，不需要再跳设置）· **收到的申请 / 已发出的申请 / 好友** 三张列表 · 底部「合作房间」区（V1.36 起是能真的建房 / 邀请 / 加入的房间系统，见 2.6）。
- **好友列表用「头像 + 名字」渲染**，行按钮按分类给：申请行「同意 / 拒绝」、发出行「撤回」、好友行「删除」（**在房间里且还有空位时**，好友行还会多一个「邀请进房」，见 2.6）。
- **双击好友行打开聊天框**（`#chat`）：`dblclick` 事件委托在 `#friend-list` 上，行内的按钮不算；聊天走 `/api/chat`（本地 `server.js` 落盘 `data/messages.json`，线上 `api/chat.js` 直连 Supabase `messages` 表，迁移见 `supabase/migrations/0006_messages.sql`），记录按「我 / 对方」左右分气泡、每条带时间戳。**双击而不是单击**是为了让「选中行」和「打开聊天」分开，避免误触。

### 好友关系

**数据模型**（`supabase/migrations/0005_friends.sql`）：`public.friendships(requester, addressee, status, created_at, updated_at)`，主键 `(requester, addressee)`，`status ∈ 'pending' | 'accepted'`，并带 `requester <> addressee` 约束。

- **一张表存双向状态**：「互为好友」= 存在一行 `accepted`（方向不敏感，查询时两向都查）。不维护「两行互为镜像」，因此**不会出现两行状态不一致的脏数据**。
- 三种视角的判据：`requester=我 and status='pending'` = 我发出去还没被处理；`addressee=我 and status='pending'` = 别人申请我还没处理；存在 `accepted` = 已是好友。
- **权限收紧**：RLS 开启且**零策略** + `revoke all from anon, authenticated`，只有服务端 service 密钥能访问；**刻意没把它加进 Realtime 发布**（谁跟谁是好友是隐私，不像 `scores` 是公开数据）。

**接口契约**（`api/friends.js` 与本地 `server.js` 完全一致；**全部需令牌**，身份取自令牌而非请求体）

| 方法与路径 | 用途 |
|---|---|
| `GET /api/friends` | 拉取 `{ ok, friends, incoming, outgoing }`，每项形如 `{ username, avatar, at }`（按用户名排序） |
| `POST /api/friends` `{action:'request', username}` | 发好友申请；**对方也申请过我 → 直接成为好友**；已是好友则原样返回 |
| `POST /api/friends` `{action:'accept', username}` | 同意对方发给我的申请（`pending` → `accepted`） |
| `POST /api/friends` `{action:'decline', username}` | 拒绝对方申请 / 撤回我发出的申请（删掉那一行 pending） |
| `POST /api/friends` `{action:'remove', username}` | 删除好友（两向关系都删） |

- 加自己、加不存在的账号分别返回明确错误；客户端**不能**替别人操作（无 `me` 参数）。
- 实时性：好友面板打开时**每 8 秒轮询一次**（`FRIENDS_POLL_MS`），关面板即停 —— 因为该表未进 Realtime。

**前端流程**（`js/game.js` 的「好友与头像」一区）

| 函数 | 作用 |
|---|---|
| `loadFriends()` / `friendAction()` / `addFriendFromInput()` | 拉列表 / 执行 action / 发申请（离线存档时提示「好友功能需要联网账号」） |
| `renderFriends()` / `renderFriendBadge()` / `renderMeAvatar()` | 渲染面板三张列表 / 主页入口红点徽章 / 我的头像 |
| `openFriends()` / `closeFriends()` / `openChat()` / `chatApi()` / `chatSendApi()` / `startFriendsPolling()` | 面板开关、聊天开关与收发、轮询 |

- 好友名来自别的账号，渲染一律 `textContent` 赋值、不拼 HTML（防 XSS）。
- 令牌失效（401）统一走 `sessionExpired()` 回登录页。

### 入口按钮（V1.35 改）

- `#btn-friends`（好友 SVG 图标）+ `#friend-badge`（红点）**竖排在设置齿轮正下方**（`.head-stack` 里两个按钮）。红点数字 = **收到的申请条数**，为 0 时隐藏。
- **V1.34 的 `#home-side` 常驻好友栏与 `#tab-home.active { padding-right }` 已删除**，主页不再为它让出通道；「＋加好友」入口移到好友界面内部（`#friend-input` + `#friend-add-btn`）。

### 头像系统

- **只存「用哪种模型」，不存图片**：`meta.avatar = { kind:'char' }` 或 `{ kind:'monster', type }`。`kind:'char'` = 用当前**角色外观**渲染，永远跟着 `meta.character` 走（改外观头像一起变）。
- **11 个选项**（`AVATAR_ITEMS`）：角色外观 + **10 款怪物模型**（`AVATAR_MONSTERS`：杂兵 / 疾行怪 / 远程怪 / 自爆怪 / 猎人 / 治疗兵 / 护盾兵 / 召唤兵 / 精英 / 首领）。名字与描边色块复用 `ENEMY_TYPES`。**树怪 `treant` 不在列** —— 它有独立的 `drawTreant()`、不吃 context 参数。
- **渲染**（`drawAvatar(c, x, y, r, av, character)`）：方形裁剪 → `kind:'monster'` 时把怪物模型画进一个 `{ x:0, y:0 }` 的假实体（`drawEnemyModel(e, color, avatarCtx)` 新增可选的第三参数，靠同名参数遮蔽全局 `ctx`）；否则画角色外观（`drawCharacter`）。**非法值一律退回「角色外观」**（`validAvatar()`）。
- **选择入口**：角色页（`#tab-char`）「头像」选择组 —— 色块 chip + **72px 实时预览**（chip 只有色块，看不出模型细节）。
- **公开副本约定**：好友列表要显示**别人的**头像，而 `users.meta` 是**整个存档**（金币 / 解锁 / 装备 / 设置），不能为了看头像就暴露 meta。所以前端保存存档时（`PATCH /api/users` / 注册）顺带把 `meta.avatar` 的副本写进 **`users.avatar` 列**，好友接口**只读 `username, avatar` 两列**。
  - 取舍：对方若用「**角色外观**」当头像，我们**还原不出他自己的配色**（那是他的 meta），一律退回**默认外观**渲染，靠用户名区分是谁（传 `null` 会错误地落到「我自己的 `meta.character`」）。

### 存档结构 v2 → v3（V1.35 续到 v4）

- `META_SCHEMA = 4`。`META_MIGRATIONS` 两步：**v2 → v3** 新增头像（默认「用角色外观」）；**v3 → v4** 新增首局引导状态 `guide: { done:false, seen:{} }`（见 10.7）。`normalizeMeta` 里对非法头像兜底为 `defaultAvatar()`、缺失的 `guide` 补默认值。老档自动升级，玩家无需操作。

## 2.6 合作房间（V1.36）

> 本轮只做「**房间系统**」：建房 / 邀请好友 / 输入房间码加入 / 双方就绪。**V1.36 时对局同步尚未实现**（双方都点「准备」也只是大厅里的状态位，不会真的开局）；**V1.37 已补上「能一起打」的同步内核**（见 2.7），房间面板上的「开始双人对战」现在会真的开局。

### 数据模型（`supabase/migrations/0007_rooms.sql`）

| 表 | 字段 | 说明 |
|---|---|---|
| `public.rooms` | `code`（主键）· `host` · `guest` · `host_ready` · `guest_ready` · `created_at` · `updated_at` | **房间码就是主键**，不用自增 id |
| `public.room_invites` | `code` · `inviter` · `invitee` · `created_at`，主键 `(code, invitee)` | 一间房可以同时邀请多个人 |

五条刻意的取舍：

- **房间码 = 6 位、字母表去掉 `I / O / 0 / 1`**（`ABCDEFGHJKLMNPQRSTUVWXYZ23456789`，32⁶ ≈ 10 亿种）—— 好友之间靠嘴念、靠手打都不会认错，也是邀请链接里唯一要带的东西。前端只负责「去空白 + 大写」，格式校验在 `coopCodeOk()`。
- **一个账号同时只在一个房间里**：建房 / 进房前服务端先把自己在别处的席位清掉（我是房主 → 那间房**解散**；我是访客 → 只**腾出**席位）。否则会出现「我同时在两间房」的鬼状态。
- **邀请单独一张表**：一间房可以同时邀请多个人，谁先点「加入」谁成为 `guest`，其余邀请在**进房 / 解散**时一并清掉；被邀请方还能单独「忽略」。
- **超过 2 小时没动静的房间**在下次有人建房时被顺手清掉（没有定时任务，也不需要为一个大厅表上 cron）。
- **权限**：两张表 RLS 开启 + **零策略** + `revoke all from anon, authenticated`，**刻意不进 Realtime 发布**（「谁在哪个房间、邀请了谁」比好友关系更接近隐私），实时性用前端 **3 秒轮询**兜底。

### 接口契约（`api/rooms.js` 与本地 `server.js` 完全一致；**全部需令牌**，身份取自令牌）

| 方法与路径 | 用途 |
|---|---|
| `GET /api/rooms?code=<code>` | 房间快照 `{ ok, room }`；房间不存在时 `room: null`（不是报错） |
| `GET /api/rooms?invites=1` | 我收到的邀请 `{ ok, invites: [{ code, inviter, avatar, at }] }`（房间已散 / 已满 / 我是房主的一律不列出） |
| `POST /api/rooms { action:'create' }` | 建房（房主 = 我），返回 6 位房间码 |
| `POST /api/rooms { action:'join', code }` | 以访客身份进房 |
| `POST /api/rooms { action:'ready', code, ready }` | 切换**我自己的**就绪状态 |
| `POST /api/rooms { action:'invite', code, username }` | 邀请好友进房（**必须已经是好友**、房间还空着） |
| `POST /api/rooms { action:'leave', code }` | 离开（**房主离开 = 解散房间**，访客离开 = 腾出席位） |
| `POST /api/rooms { action:'decline', code }` | 忽略收到的邀请（只删我这条邀请，不进房） |

错误口径：房间不存在 / 已解散 **404**、缺 `code` **400**、房间已满 **409**、不是好友 / 不在这个房间 **403**。

返回的 `room` 快照字段与前端 `coopRoom` 一一对应：`{ code, host, guest, hostReady, guestReady, hostAvatar, guestAvatar, at }`（头像从 `users.avatar` 公开副本现查，房间里不另存一份）。

- 删号会**顺带清掉**我建的房、我在别处的席位、以及两个方向的房间邀请（与 `scores` / `friendships` / `messages` 同一套做法）。

### 前端流程（`js/game.js` 的「合作房间」一区）

| 函数 | 作用 |
|---|---|
| `coopCreate()` / `coopJoin()` / `coopLeave()` / `coopToggleReady()` | 建房 / 加入 / 离开 / 准备（离开时房主看到「已解散房间」） |
| `coopCopyInvite()` / `coopInviteLink()` | 复制 `https://<站点>/?room=<房间码>` 邀请链接；无剪贴板 API 或写入失败时，退化为提示手工转发房间码 |
| `coopInvite(username)` / `coopDecline(code)` | 邀请好友进房 / 忽略收到的邀请 |
| `renderCoop()` / `coopSlotEl()` / `coopInviteEl()` | 渲染房间面板（两个席位 + 准备 / 离开）与收到的邀请（「加入 / 忽略」） |
| `loadCoopInvites()` / `refreshCoop()` / `startCoopPolling()` | 拉邀请（**进主页就拉**，因为邀请也算红点）/ 3 秒轮询（面板开着才轮询） |
| `coopHandleUrl()` | 读 `?room=<code>`：自动打开好友面板并把房间码填进输入框（**整次会话只处理一次**，不会每次回主页都把面板弹出来） |

- 房间码与好友名来自别的账号，渲染一律 `textContent` 赋值、不拼 HTML（防 XSS）。
- 令牌失效（401）统一走 `sessionExpired()` 回登录页；退出登录时清空 `coopRoom` / `coopInvites`，不留给下一个账号。

### 界面（`#friends` 底部「合作房间」区）

- **不在房间里**：`#coop-create`（生成房间码）+ `#coop-input` / `#coop-join-btn`（输入房间码加入）。
- **已经在房间里**：`#coop-code`（6 位房间码，金色大字）+ `#coop-copy`（复制邀请）+ **两个席位**（头像 + 名字 + 「房主 · 已准备 / 未准备」，空席位显示「等待好友加入…」）+ `#coop-ready`（准备 / 取消准备）+ `#coop-leave`（离开房间）。

## 2.7 合作对局（V1.37）

> 第一批只做「**能一起打**」的内核：房主权威 + 客机回放 + 跨玩家判定 + 各自选卡。**结算页、快照插值、打击反馈、双人难度放大、合作榜都还没做**（清单见第 12 节）。

### 核心思路：不是「两份状态」，而是「一份状态 + 当前代表谁」

战斗代码里到处直接读写 `squad` / `soldiers` / `stats` / `weapons` 这些全局名（40 多个函数）。与其把它们全部参数化成 `(player, ...)`，本版**只加一层「当前生效玩家」的槽位**：

| 函数 | 作用 |
|---|---|
| `makePlayer(id)` | 造一份玩家的完整 build（自己的 `squad / soldiers / hp / stats / weapons / summons / pet / skills / pickCount / routePicks / appliedIds / dmgBonus / dmgBase`，以及 `lightningCdT / lightningPending / hurtBy / lastHurt / petRunExp` 这几个零散对局态） |
| `players[]` / `P1` / `activePlayer` | 槽位数组（顺序即渲染顺序）/ 第一位玩家（复用对象）/ **当前生效的那一位** |
| `captureCtx(p)` / `loadCtx(p)` | 把全局镜像回 `p` / 把 `p` 灌进全局 |
| `switchTo(p)` / `withCtx(p, fn)` | 换人（已是目标则**空操作**）/ 临时借用某人的上下文跑一段代码再换回来 |
| `playerOf(s)` / `soldiersOf(p)` / `squadOf(p)` / `hpOf(p)` | 按 `s.owner`（玩家 **id**）解析归属 / 读某人的数组或血池（**一律走全局，避免读到陈旧的槽位字段**） |

两条硬性约定：

- **`soldier.owner` 存玩家 id（数字），不存玩家对象引用** —— 引用会让 `soldiers ⇄ player` 成环，`saveRun()` 的 `JSON.stringify` 抛错后被 try/catch 吞掉，`meta.run` 静默置空（「返回主菜单后继续」失效）。回归台有断言守住。
- **单人局 `switchTo(P1)` 是空操作**（`players` 长度 1），所以单人玩法**零开销、零行为变化**。

**哪些全局要按玩家分**：判断标准是「它描述的是一名玩家的对局状态，还是这一局的世界」。前者一律进槽位（除上面那批 build 字段外，还有 **`lightningCdT` / `lightningPending`（雷电那条线的硬性触发间隔）、`hurtBy` / `lastHurt`（受伤来源统计）、`petRunExp`（宠物熟练度）** —— 它们原本是全局单份，双人下会互相干扰：客机打出的雷会卡住房主的雷、两人的受伤混进同一份阵亡原因）；后者保持全局（`enemies` / `bullets` / `wave` / `kills` / `runCoins` / `gameTime` / `xp` / `level` / `rerollLeft`…）。**表现层的东西（`shake` / `hitStop` / `damageNumbers` / `banner`）也保持全局**，它们本来就在房主侧算 —— 其中伤害数字 / 浮动文字 / 震屏现在会随 `fx` 消息同步给客机（见下），顿帧与音效还没同步。

### 同步模型：房主权威 + 客机回放

| 环节 | 做法 |
|---|---|
| 传输层 | Supabase Realtime 的 **public broadcast 频道** `room:<房间码>`，手写 Phoenix 裸 WebSocket 协议（`phx_join` → `phx_reply` → 心跳 → `broadcast`）。**实测 public 频道不走 `realtime.messages` 授权策略 → 零 DB 迁移** |
| 上行 | 客机把移动意图发成 `in`（`joyVec()` 的值，**变化了才发**） |
| 下行 | 房主以 `NET_SNAP_MS = 55`（约 **18Hz**）广播 `snap`：时间 / 波次 / 等级 / 经验 / 击杀 / 金币 / 难度 + 两名玩家的坐标 · 朝向 · 血量 · 护盾 · 小兵坐标 · 武器，以及敌人 / 子弹 / 掉落 / 敌弹的渲染字段（坐标压到 1 位小数） |
| 客机 | **不跑 `update()`**（`netGuestTick()` 只做「贴快照 + 算镜头」），世界完全由快照驱动；`netApplySnap()` 对**自己那条小队 / 血池**用 0.35 系数插值，对世界实体直接替换 |
| 打击反馈 | 房主把 `spawnDamageNumber` / `spawnFloatText` 产生的条目攒进队列，随快照节拍额外发一条 `fx { shake, f }`（**纯表现、可丢**，一次最多 12 条，没有反馈也没震动就不发）；客机（`netGuestFx()`）摆进自己的 `damageNumbers` 并把 `shake` 取较大值 —— 这两个本来就是渲染层自己的数据，与「灌世界 + `render()`」同一套做法 |
| 开场 | 房主广播 `run:start`（**只带种子与模式**），两边各自 `reset(seed)` 得到同一张地图；客机 `reset` 后**把槽位重排成 [房主, 我]**（`me.id = 1`），再回一条 `run:go` |
| 结局 | 房主广播 `run:end` / 断线 → 两边 `netAbort()` 退回大厅，并把槽位还原成单人 |

三个必须保留的坑：

- **`netConnect()` 要等 `phx_join` 被服务端确认后才 resolve** —— 早于确认就发广播会被服务端**静默丢弃**（房主的 `run:start` 就是这么丢的：不报错、也收不到）。
- **开局消息只发种子**，不要把 `obstacles / vines / decorations` 塞进去（体积能到上百 KB）。
- **客机必须在建房 / 进房时就把通道接好**（否则 `netSend()` 全部返回 false，输入根本发不出去）。

### 跨玩家判定

- 敌人索敌本来就是**小兵级**（`nearestSoldier`），现在**跨全部玩家**找最近的小兵；`forEachSoldierAll(fn)` 同理。
- 半径类判定统一走 `anySoldierIn(x, y, r)`：**逐个玩家用「那名玩家自己的」`bodyR()`**（读他自己的 `stats.bodyMul`）—— 「小小巨人 / 大大巨人」的碰撞体积因此各算各的。
- 覆盖面：自爆怪爆炸、首领冲锋撞击、首领震波、首王砸落、精英爆炸、敌弹命中、**敌人与小队站位分离**（7 处）。
- `damageSoldier(s, dmg, cause)` 按 `s.owner` 切到该玩家上下文再结算；跨帧效果带 `owner`（子弹用 `stampNewBullets()` 按数组长度差给「本段新产生的」打戳、延迟落雷、宠物持续技）。
- **全灭判据**＝**两名玩家都不剩小兵**（单人局等价于原来的「本机没有小兵」）。
- **执行顺序**：`update()` 拆成 `updatePlayerCombat(p, dt)`（移动 / 护盾 / 技能 / 开火）与 `updatePlayerCompanions(p, dt)`（召唤物 / 宠物）两个相位，**刻意夹住 `updatePendingLightning`** —— 单人局的顺序与改动前完全一致。镜头由 `update()` 统一算。

### 升级 · 各自选卡

- **等级与经验共享**（谁捡到都算），但**候选各抽各的**：`beginLevelUp()` 逐人 `rollPickFor(p)`（在各自上下文里 `pickUpgrades(choiceCount)`），所以 `pickCount / routePicks / appliedIds` 都是各自的，两人的卡池互不影响。
- **世界在所有人都选完之前保持冻结**；本机先选完会显示「已选好，等待队友…」，不会对着同一组卡重复点。
- 房主把**给客机抽好的候选**（`id` + 文案，客机不需要重建卡池）用 `pick` 发过去；客机点卡回 `pick:choose`，**由房主在客机的上下文里落地**（`resolvePick(players[1], id)`）—— 权威始终在房主手上。
- 实现细节：`applyUpgrade(id)` 是唯一入口（数字键 1~6 / 卡片点击 / 测试台都走它）；**候选面板（`upgrades`）与待选槽位（`player.pendingPick`）必须是同一条数组引用**（`setLocalCards()`），否则重掷之后会按旧 id 找不到卡；**待选为空一律置 `null`** —— 空数组是真值，会让「等所有人选完」永远判不成立（世界就永远冻着）。

### 收场链路（结算 · 中途退出 · 再开一局）

**通道的存活周期是「在房间里」，不是「这一局」** —— 这是这一节所有行为的前提：一局打完后两边都还在房间，房主再点一次「开始双人对战」就能直接开新的一局，不必重新进房 / 重新邀请。

| 场景 | 房主侧 | 客机侧 |
|---|---|---|
| **打完这一局**（阵亡 / 通关） | `gameOver()` 照常结算自己的账号，并广播 `run:end { won, wave, kills, level, time, coins, cause, peerCause }`（`cause` = 房主自己的阵亡原因，`peerCause` = 客机自己的，两人各记各的账） | 收 `run:end` → 用**房主下发的数字**摆出结算页，阵亡原因用 `peerCause`（客机不跑模拟，所以没有「本局学到的机制」这份统计） |
| **中途退出**（暂停里「返回主菜单 / 新游戏」、结算页的「回到大厅」） | `netLeaveMatch()` → 广播 `run:end { left: true }` → 退回大厅 | 同左；收到 `run:end { left: true }` 的一方退回大厅 |
| **断线 / 通道被关** | `netAbort()` | `netAbort()`（**保留结算页**：这一局已经结束，不该把正在看的结算数据收走） |

几条刻意的取舍：

- **联机局的金币与成绩只在房主那一侧结算**（客机的结算页写「本局金币与成绩由房主那一侧结算」）。客机没有跑过模拟，它的 `runCoins / wave / level` 只是快照的镜像；双人经济与**合作榜**都还没设计，与其在这里编一套，不如先如实说明。
- **联机局的结算页只留一个出口「回到大厅」** —— 「再来一局」会开出一局单人、把队友晾在大厅，所以隐藏掉；要看结果就重开一局（房主点「开始双人对战」）。
- **联机局不能「存进度后回主菜单」**：对局快照只保存「当前生效玩家」那套上下文（见 11.3），双人局本来就不能续玩，所以暂停里的那个按钮改成「通知队友 + 回大厅」，不再调 `saveRun()`。
- 看结算页时对方收场只**提示**、不把结算页收走（`netBackToLobby(keepResult)`）。
- 退回大厅时会把槽位还原成单人（`players = [P1]`、`P1.id = 0`、清掉待选），否则残留的双人槽位会被后面的单人局带进去。

### 本批**没有**做的（见第 12 节）

- 结算页是**房主那一份数据**（波次 / 击杀 / 时长 / 阵亡原因中的「掉血主要来自」来自房主），不是「按玩家各算一份」；客机看不到自己的击杀数 / 伤害。
- 断线重连没有、局内聊天没有。
- 快照插值只有固定系数 0.35 的平滑，没有追帧 / 外推 / 丢包处理。
- 打击反馈只同步了**伤害数字 / 浮动文字 / 震屏**：**顿帧（`hitStop`）与音效仍只在房主侧** —— 客机打怪听不到打击音（音效是逻辑层在命中时触发的，客机不跑逻辑）。
- 难度与单人一致（**双人一起打会明显更轻松**），合作榜未做。
- 联机对局**不能续玩**（对局快照只保存「当前生效玩家」那套上下文）。

## 3. 伤害模型（四种类型）

| 伤害类型 | 字段 | 归属 |
|---|---|---|
| 子弹伤害 | `bulletDamage` | 武器（步枪/散弹/机枪/狙击枪） |
| 元素伤害 | `elementalDamage` | 元素类：雷电、点燃（火焰） |
| 召唤物伤害 | `summonDamage` | 召唤物：镰刀、飞剑 |
| 宠物伤害 | `petDamage` | 龙蛋 / 火焰精灵 / 雷电虫 / 冰冻精灵（点燃仍属元素伤害） |

> **元素类与召唤物彻底分开**：雷电只吃**元素伤害**加成；镰刀 / 飞剑只吃**召唤物伤害**加成。两类都走「升级卡加算 + 进化独立乘区」的同一套算法。（火球 / 冰刺已在 V1.10 从元素线下架，实现保留；V1.27 起**火球由火焰精灵的技能占用**，见 4.4。）

**乘区规则（参考 PoE 的「增加 / 更多」、Vampire Survivors 的同类加算）**

```
最终伤害 = 基础值 × (1 + 同类加成之和) × 独立乘区
```

- **同类百分比一律「加算」**：所有"+30% 子弹伤害""-30% 元素伤害"都塞进同一加算区，最后只乘一次。
- **只有独立来源才进乘算区**：局外装备（力量护符 ×1.15）、进化终极形态（如死神镰刀 ×1.4）。
- **减益进同一加算区，并留下限**：下限**只作用在加算区这一层**（不给独立乘区加下限），四路取值如下表。这样局外装备的乘区不会被极端减益一起压掉，「数量 +1」类卡的 ×0.9 也不会叠到触底后失效。

| 线路 | 加算区公式 | 下限 |
|---|---|---|
| 子弹 | `dmgBase.bullet × max(0.3, 1 + Σ子弹加成)` | 0.3 |
| 召唤物 | `dmgBase.summon × max(0.3, 1 + Σ召唤物加成)` | 0.3 |
| 宠物 | `dmgBase.pet × max(0.3, 1 + Σ宠物加成)` | 0.3 |
| 元素 | `dmgBase.ele × max(0, 1 + Σ元素加成)` | 0（保留「可被归零」这一设计杠杆） |

- **独立乘区只做纯乘**：`w.dmgMul`（武器）/ `s.dmgMul`（元素与召唤物）/ `pet.dmgMul` 都不带下限，下限统一由上面的加算区负责。因此数量卡的 `dmgMore = 0.9ⁿ`、进化卡的 `dmgMore ×1.3~1.4` 都按原值生效，不会被下限截断。**V1.31 起武器的装备词条也写进 `w.dmgMul`**（`startGame` 里按 `weapons[0]` 乘一次），所以「锋锐 +9%」与「强力子弹」这类加算区的局内卡互不稀释。
- **装备词条的数值类不进加算区（V1.30）**：`dmgBase.X` = 饰品主属性 `damageDealt` × `(1 + 该类装备词条之和)` —— 词条**彼此相加、整体作为一个独立乘区**，不与局内卡共用的加算区混在一起。实测：同一条「弹道 T3（+12%）」在加算区里被「力量权柄 +50%」稀释后只剩 **+8%**（1.50 → 1.62），改独立乘区后是**实打实的 +12%**（1.50 → 1.68）。
- **转换卡限次**：子弹→元素的「元素法师」每局最多 2 次。
- 召唤物 / 宠物伤害同理：升级卡进加算区（`dmgAdd`），进化进独立乘区（`dmgMore`），最终折算成 `dmgMul`。
- **「数量 +1」类卡牌统一带 ×0.9 独立乘区**（飞剑 / 闪电数量卡），避免纯线性膨胀，且各自最多 4 次。

| 举例（元素法师 ×2 + 强力子弹 ×3 + 元素类 Boss 奖励） | 旧（连乘） | 现（加算） |
|---|---|---|
| 子弹倍率 | ×0.269 | ×0.3（触下限） |
| 元素倍率 | ×5.76 | ×3.4 |

**宠物的元素乘区**：宠物弹丸伤害 = 基础 × 宠物乘区 × `stats.petDamage` × `stats.elementalDamage` —— 与元素线同规则：元素加成能放大它，元素减益（如「实弹专精」的 -30%）同样作用于它，不再单独保底。

**其它进加算区的属性**

| 属性 | 说明 |
|---|---|
| 易伤 `stats.vuln` | 敌人受到的伤害 ×(1 + Σ易伤)，命中结算处只乘一次（嗜血 +20%/张）。**飞剑「剑印」的 +8~28%（V1.22）与宠物标记（龙威 +50% / 绝对零度 +25%，V1.27）也进这个加算区**，所以几者相加后只乘一次。**装备「破甲」词条（V1.30）例外**：它走独立乘区 `stats.vulnGear`，在加算区之后再乘一次 |
| 吸血 `stats.lifesteal` | 按实际造成伤害的百分比回复队伍血池（嗜血 1%/张；镰刀饮血与死神镰刀另有独立来源） |
| 回血 `stats.regen` | 固定值，回血宝珠 +2/s，不参与百分比乘区 |
| 触发型回血 `stats.bloodOrb` | 血珠：造成伤害时 5% 概率回复该次伤害的 5% |
| 点燃伤害 `stats.burnDamage` | 「严重灼伤」覆盖式叠加（+10 / 20 / 35 / 50%），只作用于点燃（基础 6/s），不连带加强雷电 |

## 4. 战斗系统

**小兵（共享血池）**：初始 1 名，站桩跟随队形。

- **血条共享**：所有小兵共用一条队伍血池 `squadHp`，上限 = 小兵数 × 单个小兵血量（`小兵初始生命 100 × 生命上限加成`）。
- 所有小兵头顶显示的都是**同一条队伍血条**；伤害统一结算进血池，**不会单独死亡**。
- **掉一格（= 一个小兵的血量）就消失一个小人**：血池不足一个小兵血量时对应数量的小兵当场消失（红色粒子），血池上限同步下调；血池见底则全部消失、判定失败。
- 受伤免疫（护盾 / 免疫时长 / 闪避）统一作用于队伍。
- 范围伤害（自爆怪爆炸、Boss 冲刺）对共享血池**只结算一次**。

### 4.1 元素类（局内获得，走元素伤害）

> V1.10 起**火球与冰刺已从元素线下架**（定义与实现保留），当前元素线只有雷电。**火球在 V1.27 被火焰精灵的技能线复用**（见 4.4）。下表保留两者的原始数值备查。
>
> **V1.32 起「雷电伤害 +30%」不只作用于这条线**：**雷电虫**（局内宠物）的普攻与技能也吃这份加成，但按 `ELE_SHARE = 0.5` **折半**、并以 `ELE_SHARE_CAP = 0.5` **封顶**（因为该卡没有上限）—— 见 4.4「宠物 × 元素线的协同」。

| 元素 | 机制 | 基础值 |
|---|---|---|
| 火球（已下架） | 攻击命中敌人时召唤，飞向最近敌人，落点爆炸 | 21 伤害 · CD 1.2s · 弹速 340 · 爆炸半径 70 · 点燃 7/s |
| 雷电 | **子弹命中敌人时按概率召唤闪电**（V1.12 改：不再是「开火」时判定，而是这一轮子弹**真的打到了敌人**才判定；判定成功后**延迟 0.15s 落雷**，让子弹先出膛），随机劈敌人（优先未劈到的目标，不足则重复劈） | 18 伤害 · **无冷却** · 触发概率**只由「额外闪电」层数决定**（0~3 层 50%，满 4 层 **100%**；V1.19 起无任何可叠加的加成） · 延迟 `LIGHTNING_DELAY = 0.15s` · **硬性间隔 `LIGHTNING_MIN_INTERVAL = 0.30s`**（V1.19 起为「窗口制」） |

> **闪电的触发规则（V1.19 起为「窗口制」）**：判定仍然要求**子弹真的打到敌人**，但不再在命中那一刻直接 roll：
> 1. **打空不触发**：这一轮所有子弹都没打到敌人 → 窗口内没有命中记录 → 不判定（旧版是开火即判定，常出现「怪还没被打到，雷先落下」）。
> 2. **命中只记一次**：「一轮」= **武器的一次开火**（`updateWeapons` 里创建 `volleyTag`，所有小兵共用同一个标记）——整轮里第一发命中时只记下 `lightningPending`，同一轮的其他弹丸（散弹的多发、穿透弹的后续命中、**其他小兵的子弹**）不重复记。
> 3. **窗口结束再判定**：一次落雷之后的 `LIGHTNING_MIN_INTERVAL = 0.30s` 算一个窗口；窗口内只要有过命中，就在窗口结束时按概率判定一次。所以**落雷频率 = max(硬间隔, 武器开火间隔)**，可以连续调。满 4 层时概率仍是 **100%**。
>
> **触发概率只有一条线（V1.19）**：`lightningChance()` 现在只看「额外闪电」层数——**0~3 层 50%、满 4 层 100%**。原先的两项加成（Boss 奖励「闪电触发概率 +20%」、进化「苍穹雷暴」的「触发概率 ×1.5」）已全部移除：满 4 层本来就是 100%，这两项在满层构建下完全是空效果，只会误导选卡。
>
> **V1.13 → V1.19 为什么要改机制**：旧规则是「命中时 roll + `lightningCdT` 拦截」，cd 还没走完的那次命中机会被白白浪费，频率于是被量化成**开火间隔的整数倍**。机枪开火 0.175s，硬间隔只要落在 `(0.175, 0.35]` 区间内就一律等效 0.35s —— 实测 0.40 / 0.35 / 0.30 / 0.25 / 0.20 五档里，中间三档全都是 **2.72 次/秒**，一点没变，想微调频率根本调不动。
>
> **实测触发频率（满射速 `rateMul = 2`，60s，V1.19）**：
>
> | 武器 | 开火间隔 | 间隔 0.35（旧值） | **间隔 0.30（当前）** | 0 层 50%（间隔 0.30） |
> |---|---|---|---|---|
> | 机枪 | 0.175s | 2.72 次/秒 | **3.15 次/秒** | 2.30 次/秒 |
> | 步枪 | 0.45s | 2.13 次/秒 | 2.13 次/秒 | 1.10 次/秒 |
> | 散弹 | 0.70s | 1.43 次/秒 | 1.43 次/秒 | — |
> | 狙击枪 | 1.00s | 1.00 次/秒 | 1.00 次/秒 | — |
>
> 只有机枪（唯一开火间隔小于硬间隔的武器）会变：2.72 → **3.15 次/秒（+16%）**；步枪 / 散弹 / 狙击受自身射速限制，完全不变。
>
> **可调性（窗口制下扫参，机枪满层）**：硬间隔 0.40 / 0.35 / **0.30** / 0.25 / 0.20 / 0.175 → **2.40 / 2.72 / 3.15 / 3.73 / 4.60 / 5.43** 次/秒，每一档都不同（旧机制下中间四档全是 2.72）。
>
> 关键点：**「增援」依然不提高闪电频率**。窗口制下 `lightningPending` 只是一个布尔标记，每轮开火只记一次；200s 实测的判定次数在 1 / 3 / 5 兵下完全一致（步枪 **222 = 222 = 222**）—— 多小兵提高的是总弹量，闪电只认「武器开火了几次」。

### 4.1b 子弹附魔与状态（V1.10）

子弹现在是**点燃 / 减速 / 冰冻**三条状态线的主入口（火球与冰刺下架后，点燃不再由武器技能提供）。

| 卡 | 层数 | 第 1 / 2 / 3 / 4 层 | 前置 |
|---|---|---|---|
| 火焰附魔 | 4 | 子弹**命中时 10% / 25% / 40% / 60%** 概率点燃 **3s**（V1.23：2s → 3s） | — |
| 霜冻附魔 | 4 | 子弹**命中时 10% / 20% / 35% / 50%** 概率减速 **2s**（移速 ×0.6 = 减速 40%；V1.23：1s → 2s） | — |
| 严重灼伤 | 4 | 点燃伤害 **+10% / +20% / +35% / +50%**（覆盖式写入 `stats.burnDamage`） | 火焰附魔 |
| 爆裂 | 1 | 被点燃的敌人死亡 → 小范围爆炸（半径 70，伤害 = 其**生命上限 5%**），被波及的敌人**再挂 2 层点燃**（双倍点燃伤害、单独叠加） | 严重灼伤 |
| 冻伤 | 4 | 被减速的敌人 **10% / 20% / 35% / 50%** 概率被冰冻 3s，并立即扣除**当前生命**的 **5% / 10% / 15% / 25%**（精英 5% / Boss 固定 1%） | 霜冻附魔 |
| 凛冬 | 1 | 被冰冻的敌人阵亡 → 小范围冰冻爆炸（半径 90，伤害 = 其**生命上限 25%**） | 冻伤 |

**状态与抗性规则**

- **三类各自独立**的计时抗性：施加成功即进入抗性，抗性期间**免疫**同类施加。时长 **普通 0.5s / 精英 1.0s / Boss 1.5s**。
- **点燃与减速不可叠加**（覆盖式：新的一层直接替换旧的强度与时长）。唯一的例外是「爆裂」，它给被波及的敌人额外挂 2 层点燃（`e.burnExtra`），结算时按 `主层 + Σ额外层` 累加。
- **状态覆盖率**：施加成功后进入计时抗性，抗性只挡「**再次施加**」，**不等状态结束就解禁**——所以持续命中时覆盖率高，停火后按剩余时长自然衰减。实测（4 层附魔、单体常驻射程内、60s）：

  | 武器（攻击间隔） | 点燃覆盖 | 减速覆盖 |
  |---|---|---|
  | 机枪 0.35s | **99.8%** | **91.7%** |
  | 步枪 0.9s | **94.7%** | **90.2%** |
  | 狙击枪 2.0s | **74.4%** | **55.7%** |

  慢射速武器才是抗性真正咬到的地方（狙击枪的减速只有 55.7%），也是 V1.23 上调时长收益最大的场景；停火后点燃还能继续烧 3s、减速还留 2s。
- **百分比伤害不进任何伤害乘区**：爆裂 5%、凛冬 25%、冻伤按当前生命 —— 都直接按生命值算，避免与四路乘区相乘失控。
- **死亡爆炸防连锁**：爆炸期间被炸死的敌人不再触发死亡爆炸。
- **持续时间倍率 `stats.statusDuration`（V1.12）**：由首领奖励「元素亲和」提供（×1.35），作用于**点燃时长、爆裂的额外点燃层时长、减速时长、冰冻时长**；**抗性时长不受影响**（否则会变成「加长自己的空窗期」）。实测（V1.23 新时长）：点燃 3 → **4.05s**、减速 2 → **2.7s**、冰冻 3 → **4.05s**，三者比例都恰为 1.35。

**冻伤的定位**：按「当前生命」扣血 → 满血目标收益最大、残血几乎无收益，是典型的**开怪削血**卡；对精英（5%）与 Boss（1%）额外设了硬上限，避免 25% × 高覆盖率直接把精英秒掉。

### 4.2 召唤物之一：镰刀（近战护卫 · 可攻可防）

**机制**：刀刃环绕角色旋转，接触敌人即造成伤害。

| 参数 | 值 | 说明 |
|---|---|---|
| 伤害 | 10 | 单次 |
| 环绕半径 | **52** | 固定，**不随体型变化**（体型卡不再把刀推远） |
| 环绕速度 | 3.5 rad/s | 约 1.8s 一圈 |
| 刀刃体积 | 12 | 渲染大小 |
| 判定半径 | **24** | 接触判定 = 判定半径 + 敌人半径，含刀刃容差 |

**核心机制**

1. **沿途贯穿**：按本帧位移线段做穿身判定（点到线段距离 < 剑身判定 + 敌人碰撞半径 `e.r`），**一趟冲刺路径上的敌人全部结算**，同一趟每只只吃一次；冷却未就绪时只穿身不结算，但仍会结束这一趟（避免贴着敌人反复穿刺）。
2. **多柄目标独立**：每帧先给各剑已锁定目标登记占位（同一敌人只归一柄），抢不到的重新索敌；索敌优先级 = 未被占用 > 只有自己刚穿过的那个 > 刚被别的剑穿过的。敌人少于飞剑时允许共享。
3. **节奏错峰**：初始冷却按柄序等分（第 i 柄 = `i/柄数 × 0.6s`），多柄不会同一时刻撞上去。
4. **护身剑阵**：敌人进到小队 80px 内时，在外追击的剑立刻放弃远处目标回身护主（不打断正在进行的贯穿滑行），剑身外圈闪一圈蓝环。
5. **惯性滑行 + 折返**：贯穿后沿剑尖滑行 0.22s → 拉到 60px 外 → 按「剩余冷却刚好够冲回去」的时机折返（用冲到接触范围的距离反推），保证每次折返都能结算伤害、不空穿。
6. **贯穿打击反馈**：命中在敌人身上留下沿剑身方向的细长白光（0.2s 淡出），不再绘制扩散圆环。使用 `performance.now()` 的绝对过期时间，在主循环及绘制前清理；顿帧、暂停、升级或后台恢复均不会让旧斩痕残留。命中瞬间 0.02s 顿帧（带 0.25s 节流）+ 轻微震屏。

**宠物 × 元素线的协同（V1.32 · 需求 8）**

宠物自带元素（`PET_DEFS[].elem`），所以它理应吃得到「自己那条元素线」的加成。逐条盘点后**只有两处是真空白**，其余早就通了：

| 加成来源 | 现状 |
|---|---|
| 元素伤害乘区 `stats.elementalDamage`（元素法师 / 元素亲和 / 力量权柄 −30%） | **已吃到**（`petSkillDmg()` 里一直乘着） |
| 减速 / 冻结的施加通道 `tryApplyFrost()` / `tryApplyFreeze()` | **已吃到** |
| **「冻伤」**（被减速 → 概率冰冻 + 扣当前生命%）、**「凛冬」**（被冰冻的敌人阵亡 → 冰冻爆炸） | **已吃到** —— 它们是 `tryApplyFrost` 的**下游**，宠物挂的减速照样触发 |
| 「元素亲和」的持续时间 +35%（`stats.statusDuration`）、局外词条「电枢」「霜心」 | **已吃到** |
| 闪电线独占的「雷电伤害 +30%」（`summonMul` → `s.dmgMul`，**同类相加且无上限**） | **V1.32 接上** |
| 「霜冻附魔」的减速参数（`FROST_MUL 0.6` / `FROST_TIME 2`） | **V1.32 部分接上**（原本只挂在子弹命中上） |

- **雷电虫吃闪电线增伤**：`petSkillDmg()` 与普攻（`firePetBullet()`）统一乘 `petEleLineMul()`，即
  **`1 + min(ELE_SHARE_CAP, ELE_SHARE × (s.dmgMul − 1))`**，取 **`ELE_SHARE = 0.5` / `ELE_SHARE_CAP = 0.5`**。
  折半 + 封顶的理由：「雷电伤害 +30%」这张卡**没有上限**，直接乘满会让「投电系 = 白赚一条武器线」（满技能 8.22 → ×1.9 = 15.6，已等于一条武器线），与「宠物 = 辅助」的定位冲突。
- **冰霜领域吃霜冻附魔**：`slowMul` / `slowTime` 走「取大不叠乘」—— 强度 `min(0.45, 0.6)` 仍取宠物自身更强的那个（**不会被削弱**），时长 `max(1.0, 2.0)` 抬到 **2.0s**。刻意**不套**附魔的概率门（10~50%），因为领域的减速本来必中，套概率门反而是负体验。
- 生效范围：`petSkillDmg()` 在**释放瞬间**就把结果存进 fx 的 `f.dmg`，所以**改一处即全覆盖**（含雷电场 / 冰霜领域这类持续技的每 tick 结算）。

**实测（Lv.1 / ★1、170px 单体靶子、清空其他怪、只留宠物，90 秒，宠物总输出）**

| 闪电卡张数 | `s.dmgMul` | 元素线倍率 | 连锁闪电 | 雷电场 | 雷暴 |
|---|---|---|---|---|---|
| 0（基线） | 1.00 | 1.000 | **6.04** | **7.20** | **6.27** |
| 1 张 | 1.30 | 1.150 | 6.95 | 8.28 | 7.74 |
| 3 张 | 1.90 | 1.450 | 8.76 | 10.44 | 9.65 |
| 6 张 | 2.80 | **1.500**（已封顶） | — | — | — |

- 倍率是**精确定值**：连锁闪电 6.04 × 1.45 = **8.76**、雷电场 7.20 × 1.45 = **10.44**，逐位吻合。雷暴因为落点随机（走 `rngCombat`），单次会有 ±5% 抖动。
- 基线 **6.04 / 7.20** 与 V1.28 记录**逐位一致**，说明测量口径没变、旧数据可以直接对比。
- 冰霜领域：无附魔 `fx.slowMul 0.45 / fx.slowTime 1.0`（敌人 `frostT` 峰值 **1.48**）→ 霜冻附魔 ×1 后 `fx.slowMul 0.45 / fx.slowTime 2.0`（`frostT` 峰值 **1.98**）。

> **碰撞体积（V1.17 新增）**：上表的 `r` 就是每只敌人的碰撞半径，进图后受三重约束——
> ① **怪物之间互不重叠**（`separateEnemies()`：按半径反比分配推开量，体型越大被推得越少；**首领不被小怪推动**，否则冲刺轨迹会被一堆小怪挤歪）；
> ② **怪物与玩家不重叠**（`separateEnemiesFromSquad()`：把敌人逐个推出小兵的碰撞圈，小兵半径 `S.soldierR = 14`）；
> ③ 仍会被木桶 / 箱子 / 石柱 / 树木阻挡（`resolveObstacleCollision`，**前后各解一趟**——中间的推挤会把敌人挤进树木 / 石柱里，收尾补一趟把穿障深度从 32.5 压到 5.79；穿障比轻微重叠更显眼，所以障碍物优先级最高）。
>
> **①与②交替迭代 2 趟**（而不是各跑各的）：小兵会把敌人压成一层「壳」，壳上装不下时两个约束会互相破坏对方的结果，交替投影收敛更彻底——40 只怪全挤在玩家身上的极端场景，最大重叠深度 4.91 → **3.33**（世界单位，≈2.5 屏幕像素）。
>
> 分离正好把敌人停在「相切」，所以**接触伤害的判定额外留了 `CONTACT_PAD = 6` 的余量**（`d < e.r + S.soldierR + 6`，自爆怪的引爆判定同样用它）——贴住编队的敌人照样能打掉血，**不重叠不等于打不到**。
>
> 副作用（有意为之）：敌人被玩家推开——玩家移动时会「犁」着身前的小怪走。这是有碰撞体积后的必然结果。

**波次与出怪节奏（V1.18 重做：不再等清场）**

- **波次由计时推进**：每波固定 **`WAVE_TIME = 20s`**，到点即 `wave++`，**不再等「本波刷完 + 场上清空」**。旧规则把节奏完全交给玩家的清怪速度——清得快就越推越快、清不干净就永远卡在同一波；现在节奏由时间决定，玩家强度体现在「能不能压住不断累积的怪」，「清空」也不再是唯一的喘息窗口。
- **出怪走纯速率**：`spawnInterval() = max(0.10, 4.8 / pace)`，其中 `pace = (1 + 0.35 × (波次 - 1)) × min(2.0, spawnScale())`。每波实际出怪量 ≈ `20s ÷ 间隔`：

  | 波次 | 1 | 5 | 10 | 20 | 30 | 50 |
  |---|---|---|---|---|---|---|
  | 出怪间隔 | 4.8s | 2.0s | 1.16s | 0.36s | 0.22s | 0.13s |
  | 每波约 | **4 只** | **10 只** | **17 只** | **55 只** | **93 只** | **151 只** |

- **同屏上限 `MAX_ALIVE = 180`**：刷到这个数量就先停手，等玩家清掉一批再继续（防止后期堆积到卡顿）。
- **首领存活 / 场地封锁期间波次计时暂停**：否则上一只首领还没死就会刷出下一只，两个竞技场还会互相覆盖。精英波不冻结计时。
- 首领与精英仍是**波初投放**：第 10 / 20 / 30… 波开局刷首领，第 5 / 15 / 25… 波开局刷**一群精英**（数量见 4.5「精英词缀」）。
- 升级面板打开、暂停时 `update()` 直接返回，所以**计时也一并冻结**，不会在选卡时偷偷推进。
- **两种模式的结算条件（V1.32）**：**标准模式**在波次推进到 **21**（即打完第 20 波）时立即**通关结算**，解锁无尽模式，成绩按实际打完的 **20 波**上报；**无尽模式**没有波数上限，一直推到阵亡。判定写在波次推进处（`updateSpawning` 的 `wave++` 之后），首领 / 精英的波初投放规则两种模式完全一致。

**敌人出招预警（V1.35，验收标准：受击前 ≥0.5 秒）**

> 只有「**技能**」才有前摇 —— 普通小怪（grunt / fast）的贴身碰撞仍是即时结算，否则前期手感会变得很钝。预警全部是**渲染层**画出来的（`drawEnemyWarnings()`，只读不写、不消耗随机流）。

| 前摇 | 时长 | 表现 | 判据 |
|---|---|---|---|
| 远程怪 / 猎手开火 | **0.55s**（`ENEMY_WARN_SHOT`） | 本体亮起蓄能光点 + 一条拉向当前目标的**虚线瞄准线**，蓄能期间站定不出手 | 目标走出射程就取消蓄能（`warnT = 0`） |
| 首领八向弹幕 / 弹幕者技能 | **0.5s**（`ENEMY_WARN_MIN`） | 本体外一圈**向外扩张的蓄能环** | 弹幕者先选招（`burstWarnT`），到点才 `fireBarrageSkill()` |
| 精英近战 | **0.5s** | 地面上**红色扇环**，半径 = 实际命中距离（`e.r + bodyR() + CONTACT_PAD`） | 前摇 + 冷却合计仍 **1.0s**，**DPS 与旧版一致**，只是从「瞬间扣血」改成「看得见的一击」；玩家跑出范围就落空 |
| 分裂者突进撕咬 | **0.5s** | 本体外一圈橙色警示环 | 前摇结束才按**当时**的目标方向扑出去 |
| 首领冲锋 | 1.0s（连冲段 **0.45 → 0.5s**） | 已有的地面指示带 | `enterBossCharge()` 对传入的前摇取 `max(wind, 0.5)` |

- **第一次遇到精英怪**（每局第一次 `spawnEliteGroup`）额外给一段明确的登场提示：横幅换成「**精英怪来袭！它们贴身时会先亮起红圈再出手**」并延长到 3.0s（之后恢复「精英来袭 ×N」1.6s）。玩家在此之前还有 HUD 的「精英 mm:ss」倒计时做前置预警（见 10.1）。

| 类型 | 血量 | 掉落 | 外观 |

> **首领碾压（V1.20）**：首领碰到木桶 / 箱子 / 石柱会**直接碾碎**（V1.21 起**不给任何奖励**：金币与经验都不掉），用来解决「首领抵住障碍物后只能靠冲刺脱身」的卡脚问题。普通小怪 / 精英**不会**碾碎任何东西；石柱对子弹仍是无敌掩体，只有首领接触才会碎。判定在 `crushObstaclesByBosses()`，必须跑在 `resolveEnemyCollisions()` 的推出之前——否则首领先被推开，这一帧就不再接触了。

## 5. Boss 战

- 每 10 波 1 个 Boss，种类按 10 波冲锋 → 20 波弹幕 → 30 波召唤 → 40 波分裂 → 循环。
- **首个 Boss 的出场演出（V1.31）**：本局**第一只** Boss 不再「凭空出现」—— 先在**玩家脚底**画一个预警圈读秒 **2.6s**（`BOSS_DROP.wind`），然后从 **560** 高度砸下，落地造成半径 **190** 的一次 **45** 点范围伤害（再乘难度倍率），随后进入正常首领战（竞技场照旧以玩家为场心）。演出**每局只播一次**（`bossDropDone`）；调试面板「立刻出 Boss」与带显式坐标的刷怪**都跳过演出**，避免影响测试。
- 通用行为：**轨道走位 + 爆发位移 + 接触伤害 + 周期性弹幕**（V1.25 重做，见下），出场与狂暴均有居中横幅提示。
- **首领「灵活性」层（V1.25 新增）**：首领移速只有 28~40，而部队是 240 —— 直线追击毫无意义，首领实质是「站着放技能的炮台」。因此**不加基础移速（数值不动）**，改为给它两件事（原先还有第三件「滑步闪避」，**V1.25.1 已整体取消**：首领技能都有明确前摇，「读前摇 → 走位躲开」才是博弈点，横移一下只会让前摇读不清、动作突兀）：
  - **轨道走位**：每个种类有自己的「目标距离」`orbitR`（冲锋者 150 / 弹幕者 300 / 召唤者 300 / 分裂者 110）。径向修正**按偏差比例给**（偏离 `orbitR` 达到 `BOSS_MOVE.band = 45` 时给满速，内部线性缩放），越接近目标距离修正越小，首领真正停在 `orbitR` 上；其余时间**横向绕圈**，绕行方向在出场时随机定一次（`orbitDir`，**之后不再翻转**），朝向按 3.2 rad/s 平滑过渡（不瞬间改向）。走位仍然吃时缓 / 霜冻减速，冰冻时完全不动。
    - **V1.26.2 修正**：旧版是「出了 `orbitR ± 60` 的死区才修正」的开关式（在死区内完全不修正），首领于是停在死区边缘 —— 实测冲锋者停在 **206**、分裂者停在 **60**（目标分别是 150 / 110）。改成比例修正后，实测稳定距离收敛到 296 / 300 / 300 / 109。
    - **V1.26.3 修正**：旧版还会每隔 2.5~5.5s（V1.26.2 拉长到 6~11s）翻转一次绕行方向，但首领只有 28~40 移速（60 秒才走 168° 的弧），**每次都是走一小段就原路折返** —— 实测 60 秒净绕行只有 **-26°**（绝对绕行 88°），看起来像走 S 形，距离还被折返甩到 318。现在方向固定，净绕行 = 绝对绕行（弹幕者 60 秒 **86°**，ASCII 轨迹是一段完整的弧），距离收敛在 **300**。
  - **爆发位移**：一次性接管移动的短促位移，距离 = 速度 × 时长，末帧按剩余时间结算（不多走一帧）。目前只有两处，都是**带伤害的招牌技能**：冲锋者冲刺（880 × 0.42s ≈ 370）/ 分裂者突进撕咬（760 × 0.26s ≈ 198）。**V1.25.1 停用**：弹幕者「后跃 180」与召唤者「闪现 340」这两种**纯挪位置、无伤害**的位移（代码已注释，入口 `bossLeap` 保留），理由是位移读不出前摇、表现突兀。
  - **位置约束**：首领不越出世界；有竞技场时额外限制在「场地半径 + 220」以内——它是「维持距离」型 AI，不约束会绕着玩家一路漂到玩家够不到的地方。**V1.25.1：位移（冲锋冲刺 / 分裂突进）期间只吃世界边界**（`clampBossWorld`）—— 旧版位移也被竞技场软限制顶停，会导致实际距离短于地面预警条（贴边实测差 **370.8** 单位）。
- 通用位移与技能状态机（`updateBoss`）优先级：**位移中 > 蓄力 > 施法中 > 常规走位 + 技能模组**（V1.25.1 移除了其中的「滑步闪避」一档）。位移期间完全接管移动，且**一次位移只结算一次伤害**（共享血池，不随命中人数翻倍）。
- **首领竞技场（V1.11 新增，V1.16 大幅扩大且只锁玩家）**：首领出场的瞬间，以**玩家当前位置为圆心**圈出一块半径 **600**（世界单位，直径 1200 = 屏幕可见宽度的 2 倍；旧值 270 / 直径 540）的圆形场地，同时把首领从屏幕外**拉进场内**（沿它相对玩家的方向放到 `min(0.62r, 220)` 处，保证落在视野内）。战斗中：

  **①b 协同技（V1.35 新增 8 张，同样只在首领奖励池出现）**——跨系统的「组合触发」，**每张都有自己的 `req` 前置**（与①不同，这里保留前置：没有对应组件时这张卡等于空卡，不该占位），且**第一波首领的奖励面板里不会出现**（`bossKills <= 1` 时全部过滤掉，避免新手第一只 Boss 就被塞一张用不上的卡）：

  > **冰霜火的触发通道（V1.35 修订）**：它的前置是「霜冻附魔」，而那张卡给的是**减速**（走 `tryApplyFrost`）而不是冰冻（走 `tryApplyFreeze`）。效果原本只挂在冰冻上 —— 于是玩家凑齐了两个前置、拿到冰霜火，却**看不到任何反应**（除非另外还拿了「冻伤 / 凛冬」或带冰冻的宠物）。现在**两条通道都挂**：施加霜冻（减速）与施加冰冻都会点燃。这才是「前置看起来有问题」的真正原因。

  | Buff | 效果 | 普通卡对照 |
  |---|---|---|
  | 生命上限 +50% | 队伍血池上限提升，并立刻回复等量生命 | 生命上限 +20% |
  | 易伤 +30% | 敌人受到的所有伤害 +30%（同类相加） | 嗜血（易伤 +20%） |
  | 每秒回复 +5 | 队伍血池每秒额外回复 5 点 | 无同类普通卡 |
  | 移速 +30% | 部队移动更快 | 移速 +12% |
  | 拾取范围 +100% | 经验光球磁吸更远 | 拾取范围 +30% |

  > **补位规则（V1.15）**：一次性奖励只有 6 张，所以**最多能撑满 6 格一次**——从第 2 个首领起就一定会用补位卡补齐。极端情况（一次性池已空且 N = 6）下补位卡只有 5 张，同一面板内会出现 1 张重复卡，但仍不留空格。补位卡可反复获取，是后期的无限成长出口。

> **旧名对照（V1.11 → V1.12）**：`射速 +100%` → **狂暴**（射速 100% → 66%，但新增子弹伤害 -50%）；`实弹专精` → **力量权柄**（新增射速 -20%）；`元素专精` → **元素亲和**（元素 +50% / 子弹 -30% → 元素 +35% / 子弹 -50% / 异常时长 +35%）。旧存档里的这几个 id 会自动迁移到新 id，不会重复发放。

**「力量权柄 / 元素亲和」是一对互斥的路线取舍卡**（参考 20 Minutes Till Dawn 的取舍型 Synergy）：带 `once`（拿过就不再出现）与 `exclusive: 'dmg-route'`（同组已选则对方本局不再出现）。代价只走加算区，所以另一条线之后仍可继续投资把它补回来——不会锁死任何一条路线。

## 6. 升级系统（普通升级）

- 经验条满触发；默认 3 选项，可「升级选项 +1」至最多 6（权重 1.1）。
- 卡池按权重随机（`W_LOW 0.35 / W_MED 0.6 / W_NORM 1`）；不含武器解锁。
- **重掷**：每局 3 次（击败 Boss +1），用尽后按钮隐藏。**双人时客机不显示重掷按钮** —— `rerollLeft` 是房主那边的共享计数，客机按了没有意义。
- **双人「各自选卡」（V1.37）**：等级与经验是**共享**的（谁捡到都算），但**候选各抽各的**（用各自那份 `pickCount / routePicks / appliedIds` 建池），**世界在所有人都选完之前保持冻结**；客机侧的候选由房主下发（`id` + 文案）、点选后由房主在客机的上下文里落地。实现细节见 2.7。

**四线「专精」（V1.33 · 各 3 段，数值为累计）**

> 与「质变链」的分工：质变链是**概率触发的机制**（割裂 / 剑印 / 冻伤），专精是**确定的数值成长**。
> 而且专精补的是**固定伤害** —— 之前全游戏只有「基础值 × 倍率」，这是第一处「固定值直接加到基础值上」（加完再吃该线原有乘区，所以中期不会失效）。
> **卡面显示的就是「选完这次之后的累计值」**（不是本次增量），`desc` 在 `buildUpgradePool()` 每次开面时按当前层数现算。

|---|---|---|---|

| **闪电专精** | 已解锁雷电 | 雷击**获得范围伤害**：半径 **90 / 130 / 180**、范围伤害 = 本次雷击的 **30% / 45% / 60%**；闪电伤害 **+10% / +20% / +35%** | `stats.lightningSplashR / lightningSplashPct` → `lightningSplash()`（由 `strikeEnemy()` 调用）；`stats.lightningMastery` → `triggerLightning()` 的最后一层乘区 |

| **镰刀专精** | 已召唤镰刀 | 镰刀伤害 **+2 / +5 / +9**（固定值）、**命中冷却 -8% / -15% / -25%** | `stats.scytheFlat` / `stats.scytheHitCdMul` → `updateScythe()`（同一敌人两次命中的最小间隔） |

- **半径 90 / 130 / 180 的取值依据**：对齐局内既有的范围刻度 —— 雷暴单道雷 **80**、火球落点 **90**、熔岩 **95**、冰霜领域 **150**、霜冻新星 **180**。所以第 1 段（90）是「比一个落雷点略大」，满段（180）正好落在「霜冻新星」这一档，**不会变成清屏**。
- **范围伤害走 `hitEnemy()`**（吃易伤 / 剑印 / 护盾 / 吸血那一整套），不像落雷直击那样裸减血；**没点专精时半径 0 → 直接 return**，行为与 V1.33 之前完全一致。
- 落雷现在会额外画一圈**范围圈**（`spawnLightningBolt(x, y, radius)` 多带一个 `radius`，在 `drawLightningBolts()` 里按半径描边 + 淡填充），一眼能看出这一劈波及多大一片。
- 四张卡**都不带 `route` 字段**：不带就不会计入进化门槛的 `routePicks`，避免这 4 条线因为多了 3 张卡而**提前进化**（哪天想让它计入，各加一个 `route` 即可）。
- 火焰专精**不会凭空挂上点燃**：`applyBurn()` 在 `burnDps <= 0` 时直接返回，所以必须先有火焰来源，专精只是「把已有的点燃变强」。

**子弹穿透**：穿透次数在命中不同敌人时逐次消耗，同一发子弹不会重复命中同一敌人；穿透耗尽后子弹消失。

## 7. 护盾（带恢复）

- 护盾量 +20/张；抵挡伤害，破盾后 **5 秒**未受击开始按 **7/秒** 恢复（**V1.35：3s → 5s、10 → 7**，压掉后期「护盾一两秒就回满」的无敌感）。下限 0.5s，可被「坚定守护」削减。
- **守护线（V1.35，四级严格前置）**：`护盾 +20` → **守护**（3 次，累计护盾上限 +5 / +15 / +30，且**拥有护盾时**移速 +5% / +10% / +15%）→ **盾反**（3 次，累计受击反弹受到的伤害 **10% / 25% / 40%** 给周围敌人；**若这一次的原始伤害超过当前护盾量，护盾会炸开**：对半径 **70** 的小范围造成该次伤害 **40% / 50% / 70%** 的爆炸伤害并击退，击退初速 240）→ **坚定守护**（3 次，累计护盾恢复延迟 **-0.2 / -0.5 / -1.0s**）。四张卡按「有前置才出现」逐级解锁，卡面数值都是**累计值**。
- **受伤免疫只认「扣血」（V1.35）**：`INVULN_CD` **3s → 5s**，且触发点在「护盾吸收之后」——**只扣盾的那一下不触发免疫、也不进冷却**，避免满盾时反复刷新无敌。

## 8. 掉落与经济

- 经验光球：grunt 12 / fast 9 / ranged 15 / elite **55** / boss 320（树怪 90；木桶 8、箱子 12）。
- 金币（**V1.21 整体砍到约一半**）：普通杂兵（grunt / fast / ranged / hunter）**50% 概率掉 1 枚**（`MOB_COIN_CHANCE = 0.5`，期望 0.5，它们占了绝大多数击杀）；其余来源按面板值**必掉**——精英 **2**（旧 5 → V1.21 的 3 → V1.24 的 2）· Boss **25**（旧 50）· 树怪 **3**（旧 6）· 木桶 **1**（旧 3）· 箱子 **2**（旧 5）· 自爆 / 治疗 / 护盾 / 召唤小怪 **1**（旧 2~3）；首领碾碎的残骸**不掉任何奖励**。结算时累加。
  - 实测（自动走位 + 自动选卡）：**5 分钟不死**的一局 **209 → 100 金币**（−52%）；**被怪潮打死**的一局（约 85s）**24 → 11 金币**（−54%）。
  - 局外价格同步 **×3**（见 1. 主页的解锁价表），于是「一次 5 分钟长跑 ≈ 一颗普通蛋（200）」成为新的节奏基准（V1.21 的基准是抽蛋 180，V1.27 起蛋价见 2.1）。
- **金币不足的统一提示（V1.35）**：解锁装备 / 洗练词条 / 孵蛋这三处只要钱不够，就**不再静默失败**，而是底部浮出一条 `toast`，说清「**还差多少 + 需要多少 + 现在有多少**」（`toastNeedCoins(need)`，金币数字用金色高亮）；按钮本身也保持置灰（`.locked`）状态。三处共用同一个函数，口径一致。
- 持久化三通道：Electron 主进程写应用数据目录 → HTTP `/api/users` → 都不可用时回退 `localStorage`（key `fury_users`）。保存金币、解锁、装备、宠物养成、最佳波次、设置与**本局进度快照**。
  - `/api/users` 有两种服务端实现，对外契约一致（GET 读全表、POST 整表覆盖）：**线上**为 Vercel Serverless Function `api/users.js`，经 PostgREST 用 secret / service_role key 读写 Supabase `users` 表；**本地开发**为 `node server.js`，落盘 `data/users.json`。
  - 前端不直连数据库，`js/game.js` 不感知后端差异。Supabase 侧 `users` 表开启 RLS 且**不建任何策略**，并收回 `anon` / `authenticated` 的表权限，因此只有服务端密钥能读写（安全顾问的 `rls_enabled_no_policy` 提示属预期状态）。

## 9. 数值与平衡

**成长节奏**

- 升级节奏（**V1.35 重调曲线：前调后调**）：初始经验需求 **26**，逐级 `×1.23 + 6`（26 → 37 → 51 → 68 → 89 → 115 → 147 → 186 → 234 → 293 …）。改动目的：**前期略微抬高**（1 级 22 → 26），**后期明显放缓**（10 级 465 → 293），避免后期卡等级（V1.11 旧序列为 22 与 `×1.32 + 6`）。
- 世界成长（每击败 1 个 Boss）：**经验获取 +20%**、**出怪速度 +12%**（V1.18 起只作用于出怪间隔，因为每波怪量已由「20s ÷ 间隔」决定；间隔加速上限 **2.0 倍**，旧版是 1.6 倍），并刷新场景植物。
- **敌人随波次 / 首领数的动态成长（V1.11 重做，分前中后三段）**：
  - 小怪血量倍率 `enemyHpScale()`：
    - 前期（未击败首个 Boss）：`1 + 0.06 × (波次 - 1)`（旧版在这一段恒为 1，所以前期一直是固定血量）；
    - 首个 Boss 之后：再叠加 `0.10 × m + 0.55 × (Boss 数 - 1) + 0.008 × m²`，其中 `m = 波次 - 10`（`m²` 项让后期追得上玩家的乘区成长）。
  - 小怪伤害倍率 `enemyDmgScale()`：前期 `1 + 0.015 × (波次 - 1)`；首个 Boss 后再叠加 `0.025 × m + 0.10 × (Boss 数 - 1)`。与难度倍率相乘后生效（首领不吃这条）。
  - **重装单位折半**：`elite` / `treant` 的成长曲线按 `1 + (全场倍率 - 1) × 0.5` 折算（见 `HEAVY_HP_CURVE`）——树怪基础血量本就高，吃满整条曲线后期会反超首领；精英（V1.24 起基础 150）沿用同一档，保证后期成群时不至于硬得离谱。
  - 首领血量倍率 `bossHpScale()`：`1 + 已击败首领数`（第 1 个 ×1、第 2 个 ×2、第 5 个 ×5、第 10 个 ×10）。
  - 出怪倍率 `spawnScale()`：`1 + 0.12 × Boss 数`，击败过 Boss 后额外 +0.10 基础值并随波次增长（`+0.05 × max(0, 波次 - 10)`）。V1.18 起它**只作为出怪间隔的加速项**（除数，参与 `spawnInterval()` 的 `pace`，封顶 2 倍），不再决定每波总怪量。

    同波次旧版对照（波 50 / 4 个 Boss）：grunt 225、elite 1650（+990）、首领 1400~3200。
- 动态难度：每击败一个 Boss 难度 +0.25（上限 3 倍），影响敌人血量/伤害/速度。
- 关键上限：闪避 60%、受伤免疫 1.0s（带 3s 冷却）、**武器射速 +100%**（`WEAPON_RATE_CAP`）、升级选项 6、`DMG_FLOOR = 0.3`（只作用于加算区，元素线取 0）、**落雷间隔 ≥0.30s**（`LIGHTNING_MIN_INTERVAL`，窗口制；机枪满射速实测 3.15 次/秒）。

## 10. 打击反馈 / 音效 / 操作

- 打击反馈：伤害数字、屏幕震动、命中/击杀/爆炸粒子、**飞剑贯穿斩痕 + 0.02s 顿帧**（节流 0.25s）；普通怪与首领受击 0.09s 亮色反馈、粒子拖尾、普通子弹曳光与镰刀弧形轨迹。V1.2 移除普通击杀扩散圈与飞剑斩痕圆环，保留 0.2s 短促剑光；敌人一经标记死亡便不再绘制。敌弹使用珊瑚红外圈与浅色核心，区别于己方子弹；火球爆炸、雷电、冰刺等实际技能特效保留。
- 音效：Web Audio 实时合成（噪声缓冲 + 滤波扫频 + 包络）——射击、命中、拾取、升级、爆炸、雷击、火球、冰刺、减速等；背景为简单循环音乐。
- 操作：虚拟摇杆（触屏）+ 键盘 WASD / 方向键，二者可并存。升级卡使用原生按钮，可通过 Tab 聚焦、Enter / Space 选择，并有清晰焦点描边。
- **键盘快捷键（V1.14）**：统一由 `handleHotkey(e)` 处理，返回 `true` 表示这次按键被快捷键消费掉（消费时才 `preventDefault()`），否则交回浏览器默认行为。

  | 状态 | 按键 | 行为 |
  |---|---|---|
  | 升级面板 | `1`~`6` | 直接选第 N 张卡（等价于点卡片） |
  | 升级面板 | `R` | 重掷（等价于「重掷」按钮，次数耗尽时无效） |
  | 首领奖励面板 | `1`~`6` | 直接选第 N 项首领奖励（只结算 1 项） |
  | 对局中 | `Esc` / `P` | 暂停 |
  | 对局中 | `Q` | 时缓（等价于右下角技能按钮） |
  | 暂停中 | `Esc` / `P` / `回车` / `空格` | 继续游戏 |
  | 结算中 | `R` / `回车` | 再来一局 |
  | 开发者模式下（任意对局状态） | `` ` `` / `F1` | 开关「局内调试面板」（见 10.6b；非开发者模式下不响应） |
  | 主菜单 | 任意 | 不响应（只有上述状态才有快捷键） |

  - **面板张数**：升级面板与首领奖励面板的张数都等于当前的升级选项数（`choiceCount`，3~6），所以数字角标最多到 `6`。首领奖励的补位规则见第 5 节。
  - **数字角标**：卡面图标右下角会显示 `1`~`6` 的小角标（`.card-key`），提示「按这个数字键可以直接选这张卡」。
  - **按键越界**：卡牌不足 6 张时按越界数字键会被静默吃掉（不会落回移动键等其他逻辑）；按到没有卡片的位置不会触发任何操作。
  - **输入框内不拦截**：`isTypingTarget()` 判定登录 / 注册 / 开发者口令等 `<input>` / `<textarea>` / `<select>` / `contenteditable` 元素，在其中按键会直接跳过快捷键，避免输密码时误触暂停、选卡、重开。

## 10.1 局内 HUD 与设置

- 局内 HUD：顶部半透明面板按行展示波次、时长、击杀、金币、小队人数、护盾、队伍生命数值与血条，底部为等级和经验条；首领血条单独列在其下。画面底部显示已获得的武器、元素、召唤物和宠物标签，自动换行并避让右侧主动技能。生命低于 30% 时屏幕边缘泛红，时缓期间有青色边框；开局前 7 秒显示移动提示。
- **「本波目标」一行（V1.35 新增）**：HUD 面板的最后一行分三栏 —— 左「**剩余敌人 N**」（`enemies.length`）、中「**精英 mm:ss**」、右「**首领 mm:ss**」，倒计时 = 本波剩余 `WAVE_TIME - waveT` ＋ 中间整波的秒数（标准模式超出 20 波显示「—」）。**首领存活时这一行冻结**（波次计时本来就在首领战里暂停），右栏改成高亮的「**首领 交战中**」并展开首领血条（血条跟着下移 12px）。精英波次按 `wave % 5 === 0 && wave % 10 !== 0` 判定（第 5 / 15 / 25… 波），首领波按 `wave % 10 === 0`（第 10 / 20 / 30… 波），与 `updateSpawning` 的实际投放规则**同源**。
- **玩家名称**显示在角色上方。
- 顶部提供**暂停按钮**（居中），**右侧**是**「切换攻击目标」按钮**（V1.35 从顶部居中挪到右上角：原先它与开发者调试面板 / 信息浮层挤在同一片区域，现在两者不再重叠；调试面板展开时信息浮层会挪到左下角）。打开暂停面板，包含：
  - 继续游戏 / **新游戏**（放弃当前进度，从第 1 波重开）/ 返回主菜单
  - 对局摘要（时长 · 波次 · 击杀；击败过 Boss 后追加经验加成 / 出怪加成）
  - 显示方向：**竖屏 / 横屏**（逻辑分辨率按真实屏幕比例自动推导）
  - 帧率上限：30 / 60 / 120 / 不限
  - 环境特效：**完整 / 精简**；精简关闭萤火、经验晶体光晕和粒子拖尾，保留攻击本体与危险预警。此设置与「原始精简」界面主题相互独立。旧存档默认使用完整模式。
- **返回主菜单会保留本局进度**：整局状态（波次 / 击杀 / 等级 / 经验 / 已获升级 / 小兵 / 召唤物 / 宠物 / 场景植物 / Boss 进度 / 倒计时等）快照进账号存档（`meta.run`），下次「继续冒险」直接回到暂停界面，可继续或点「新游戏」重开。阵亡结算后自动清除该存档。
- 快捷键：Esc 或 P 暂停/继续；暂停中也可用回车 / 空格继续（详见第 10 节的快捷键表）。
- **继续游戏先走 3 秒倒计时（V1.31）**：点「继续游戏」（或按 Esc / P）不再立刻恢复，先读 **3** 秒（暗幕 + 居中大数字，每秒一次缩放脉冲），读秒期间**世界完全静止**（`update()` 直接返回，`gameTime` 不推进），给玩家一个「找回手」的窗口。
- **自动攻击目标优先级（V1.31）**：局内顶部右侧有一个**目标按钮**（显示当前档位名），点一下或按 **Tab** 循环切换 4 档 —— **最近 / 最强 / 首领优先 / 精英优先**。该档位**统一作用于所有自动索敌**：武器开火、宠物普攻与**宠物技能落点**、火球触发、以及角色持枪朝向都走同一个 `pickTarget()` —— 用于解决「弹幕者在后方放弹幕、前排又堆满高速小怪时火力全被小怪吸走」的场景。
  - **「优先」档按权重挑大档**（首领 8 / 精英 3 / 树怪 2），同档再比距离。
  - **枪口朝向只认「射程内」的目标（V1.35 修）**：`updateSquad` 里的持枪朝向改成 `pickTarget(squad.x, squad.y, 武器射程 × rangeMul)` —— 与 `updateWeapons` 真正开火的口径**完全一致**。修之前出现的是「枪死盯着一个打不到的优先目标、子弹却打身边的敌人」的错位感。射程内没有目标时：移动则朝移动方向，静止则保持上一帧朝向。
- 暂停按钮只在真正对局中显示（升级、Boss 奖励面板打开时自动隐藏）。

## 10.2 屏幕适配

- **逻辑分辨率跟随屏幕比例**：竖屏以宽 450 为基准、横屏以高 450 为基准，另一维按真实屏幕比例换算。
  - 竖屏允许区间 16:9 ~ 22:9（450×800 ~ 450×1050），横屏为其倒数，覆盖主流手机；
  - 手机屏内**满屏显示、不留黑边、不拉伸**；超出区间（如桌面宽屏开竖屏）等比留边居中。
- **高清渲染**：canvas 后备缓冲按设备像素比（上限 2 倍）放大。
- **边界视角允许越界（V1.35）**：镜头不再严格夹在世界矩形内，而是允许**在四边越界**一小段 —— `ox = min(viewW × 0.3, 300)`（上下同理）。旧版贴到地图边缘时角色会被顶到屏幕最角落、被摇杆 / 技能键 / HUD 挡住视野；越界后角色始终留在屏幕中央区（约 30%~70% 宽度），代价是边缘外露出一条深色「世界之外」的边框。
  - 副作用与兜底：世界边缘会落进视野里，所以 `spawnEnemy()` 里多了一道「**出屏兜底**」—— 若夹取后的随机落点仍在可视范围内，就沿最近的一边把它推出屏幕（只对随机出怪生效；分裂 / 召唤 / 调试这类**显式落点**就地出生，推出屏反而会瞬移）。
- **面板滚动**：`html/body` 禁止滚动，菜单/面板保留滚动能力；**V1.35 起不再显示滚动条**（`scrollbar-width: none` + `::-webkit-scrollbar { display:none }`，`overscroll-behavior: contain`），主页与各子页都按「**不需要上下滑动**」为目标排布，内容超长时才隐蔽地滚动。六选升级在竖屏纵向排列、横屏两列，重开升级面板和切换菜单页时回到顶部。
- 窗口尺寸或手机方向变化时自动重新适配（含防抖）。
- 遵循系统 `prefers-reduced-motion`：关闭界面入场动画、角色摇尾/呼吸/眨眼/抖耳/围巾摆动、萤火漂移与屏幕震动。

## 10.3 美术实现与视觉验证（V1.2）

## 10.5 协作美术规范（V1.3）

后续建模、绘制和特效应遵循以下统一特征，确保新增内容与现有画风相似：

- **总体方向**：二维 Canvas 卡通奇幻风，轮廓圆润、形体略夸张、颜色高对比；不追求写实纹理，优先保证 320×568 手机尺寸下的轮廓识别。
- **轮廓与层次**：主体使用深青灰粗描边（约为模型半径的 8%~12%），主体内部使用一到两级纵向渐变；地面统一绘制低透明度椭圆阴影，表现角色与怪物落地关系。
- **角色**：福瑞角色采用柔和脸部曲线、尖耳、双色脸颊、奶油色尾尖、渐变虹膜和少量衣物结构线；待机动画只做低幅度摇尾、呼吸、眨眼、抖耳、围巾摆动，脚底保持接地。
- **怪物**：模型必须同时表达“身体轮廓 + 职能特征 + 面部朝向”。普通怪使用耳朵、眼睛和身体姿态区分；快速怪强调瘦长与腿部动势；远程怪配法杖/投射物；自爆怪配炸弹体与引线；猎人配尖耳和弧形武器；治疗怪配十字标记；护盾怪配独立盾牌；召唤怪配兜帽与能量环；精英配护甲和棱角；Boss 配冠饰、放大比例和种类专属色。树怪保留树干、根系、树冠、发光眼和枝臂。
- **色彩语义**：己方以青绿、暖金、浅蓝为主；敌人按职能使用红/橙（攻击与爆炸）、紫（远程/召唤）、绿（治疗）、蓝（护盾/冰冻）；同色不可同时表示相反危险等级。
- **受击与状态**：受击使用短于 0.1 秒的浅色闪白；燃烧用橙红火舌和少量黑烟；冰冻用半透明多边形冰块、裂纹和霜圈；护盾用蓝色环；Boss 狂暴用红色外环。特效先表达方向和危险范围，再添加发光、粒子和震屏。
- **特效预算**：单个命中特效应在 0.2~0.45 秒内结束；粒子采用少量高亮点和渐隐拖尾，避免持续大面积半透明叠加；精简环境特效和 `prefers-reduced-motion` 必须能关闭漂浮、震屏和非必要粒子。
- **新增内容流程**：先用 Canvas 几何图形完成轮廓与命中尺寸，再补渐变、纹理和特效；每个新增敌人必须提供静态轮廓、移动姿态、受击帧、死亡反馈、危险技能预警五项；绘制函数不得修改实体坐标、伤害和碰撞参数。
- **验收尺寸**：至少在 390×844、320×568、900×450 检查轮廓、血条、技能预警和特效遮挡；新增内容需补入 `tests/visual-smoke.js`，并保持浏览器控制台 error / warn 为 0。

## 10.6 开发者模式（V1.7 新增；V1.26 起补上「局内调试面板」）

入口为**主菜单 → 设置 → 音效开关**：连续切换 10 次（常量 `SOUND_TAP_UNLOCK = 10`）后设置页底部弹出**密码验证**，密码正确才进入开发者模式。计数在**切换标签页 / 离开设置页时清零**，必须连续操作；按「取消」也会清零。

- 解锁状态写入当前账号（`meta.devMode`），换设备或重新登录依然保留；「退出开发者模式」可关闭。
- **密码不以明文出现在仓库或文档里**：代码里只存它的 SHA-256（常量 `DEV_PASSWORD_HASH`），校验在前端用 Web Crypto 比对。改密码时用新口令的 sha256 替换该常量即可。
- 这只是一道「防误触」的门，不是安全边界：游戏是纯前端，任何人读源码都能拿到哈希并爆破。它的用途是避免好友误入面板。

面板内可调项**仅对当前账号生效，改完即时保存**：

| 分组 | 可调项 | 说明 |
|---|---|---|
| 基础 | 金币、最佳波次 | 点「应用金币 / 波次」；取值分别夹在 0~9999999 与 0~9999 |
| 解锁 | 「一键解锁全部」 | 把 `SHOP` 下全部武器 / **护甲 / 饰品 / 物品**（V1.29 拆成三个槽位；V1.30 起对没词条的装备**补上第 1 条**，**不会重置**已有的洗练次数与词条），以及**全部 4 只宠物**（V1.27）写入 `meta.unlocked` |
| 宠物养成 | 宠物（下拉）、等级、星级、能量碎片 | 点「应用宠物数据」写入指定宠物；「宠物全部拉满」把**全部 4 只**宠物设为等级 / 星级上限、能量清零，并把天赋点**均摊到整棵技能树**（保证三个技能都能直接测）—— V1.27 起；V1.28 起字段由「碎片」改为「**能量碎片**」 |

| 存档 | 存档信息 | 用户名 · 存档通道 · 体积 · **结构版本（v2）** · 是否有未结束对局 · **是否有备份 / 坏档备查**（V1.32） |
| 会话 | 退出开发者模式 | 关闭 `meta.devMode` 并隐藏面板 |

- 面板只在 `meta.devMode === true` 时显示；普通玩家看不到入口，也不影响对局逻辑、数值平衡与升级卡池。

## 10.7 新手引导与首局节奏（V1.35）

**首局引导（只在「这台设备的第一次冒险」出现）**

- **形态**：屏幕下三分之一处正中央的一条提示（`#guide-tip`，项目符号 + 文案 + 进度 `n/5` + ✕）。**不锁操作、不弹窗、不遮战场**，除 ✕ 之外整条 `pointer-events: none`（绝不吞掉移动用的拖动）。升级 / 暂停面板打开时自动隐藏。
- **五个步骤各绑一个真实动作**，做到就推进一步（`guideAdvance(id)`）：

  | 步 | 文案 | 判据 |
  |---|---|---|
  | 1 | 移动：W A S D / 方向键，触屏直接拖动屏幕 | 累计移动距离 > **90** 世界像素 |
  | 2 | 拾取经验：走到绿色光球上把经验吃掉 | 收到第一个经验光球（`updateDrops` 里判定） |
  | 3 | 第一次升级：经验条满了会自动弹出三选一，选一张变强 | `openUpgrade()` 被调用（第一次升级面板弹出） |
  | 4 | 暂停：按 Esc / P，或点屏幕顶部的暂停键 | `pauseGame()` 被调用 |
  | 5 | 主动技能：按 Q 或点右下角技能键，让敌人减速 | `useSkill('slow')` 被调用 |

- **存档**：`meta.guide = { done:false, seen:{} }`（**存档结构 v3 → v4**，见 2.5）。五步走完写 `done = true`，之后**再也不出现**；点 ✕ 也可直接跳过整段（同时写 `done`）。
- 刻意不做的：不阻断操作、不强制读条、不在对局中途弹系统入口。

**前 3 波减负（`earlyEase()`）**

- 判据：`wave <= 3 && bossKills === 0`（只作用于**还没打败过首领**的开局）。
- 出怪间隔 **×1.3**（`earlySpawnMul`）· 小怪接触伤害 **×0.7**（`earlyDmgMul`）· **经验值不动**。
- **为什么不动经验**：前 3 波少刷的怪正好把「首次升级」推到 20 秒上下 —— 按出怪间隔推算（1 + (3-1) × 6.24 ≈ **13.5s** 出满 3 只，再算上清怪与走过去捡球的时间），**自动走位打法的实测值在 17~22 秒之间**（清缓存后复测：21.4 / 19.7 / 21.9 秒；每局世界种子不同、出怪落点有差异，所以断言只卡「≤ 30s」而不写死数值，回归台每次运行都会重新实测）。若同时抬高经验，首升会被提前到 10 秒出头，反而不符合「20 秒左右」。
- 第 4 波起（或击败第一个首领时）自动恢复正常节奏。

**结算页的两项新手信息**

- **阵亡原因**（`#go-cause`）：每次真正**扣到血**的伤害都带一个来源标签（`damageSoldier(s, dmg, cause)`），结算时取**最后一次**作为「阵亡原因」，再附上「本局掉血主要来自 <来源>」（按各类累计扣血排序）。五类：**近战伤害 / 范围爆炸 / 敌方子弹 / 首领技能 / 藤蔓等环境机制**；统计为空（读档续玩等）时兜底为「力竭而亡」。**通关时不显示**。只扣盾不扣血的那一下既不计入统计、也不触发受伤免疫。
- **本局学到的机制**（`#go-learned`）：`learnTag()` 在本局真正触发过的系统上打点（移动 / 经验光球 / 升级卡（最多记 4 张）/ 终极进化 / 首领奖励 / 护盾 / 暂停 / 时缓 / 首局引导完成），结算页最多列 **6** 条，超出只给一句「还有 N 条机制在下一局里等你发现」。**不一次性铺开所有系统入口**。

**移动端防误触（验收项）**

- 面板可以拖动滚动，拇指「按下 → 拖着走 → 松手」时 `pointerdown` / `pointerup` 常落在同一个按钮上，浏览器仍会派发一次 `click`，于是**滑一下就误选了升级卡 / 误按了返回键**。
- 做法：全局手势守卫（捕获阶段，早于元素自己的 `onclick`）—— 本次手势位移 > `TAP_SLOP = 12px` 的一律不算点击，只对「点错代价大」的元素生效：`.card`（升级三选一）/ `.nav-back`（各页返回）/ `#btn-pause` / `#btn-aim` / 结算的「再来一局 · 返回主菜单 · 继续」。
- 另外给局内按钮加 `touch-action: manipulation`（避免 double-tap 缩放吞掉一次点击）。

**同批修掉的一个渲染崩溃**

- `loop()` 的单帧 `dt` 之前可能为**负数**（`startGame` / `resumeGame` 会把 `last` 设为 `performance.now()`，而 rAF 回调拿到的是**本帧开始**的时间戳；若这一帧中途跑了长任务，`now < last`）。负 dt 会让所有 `x -= dt` 的计时器**倒着走**——实测落雷特效 `life` 反涨到 `maxLife` 的 1.4 倍，画出**负半径**的地面环，`ctx.ellipse` 直接抛 `IndexSizeError`，打断整帧渲染。
- 修法：把帧间隔换算抽成 `frameDt(raw) = clamp(raw/1000, 0, 0.05)`（下限 0、上限仍是原有的「单帧最多推进 50ms」），并在 `drawLightningBolts()` 里把进度 `k` 钳到 `[0,1]` 作为渲染层的二次防线。

## 11. 架构约定（V1.32）

### 11.1 状态机（`STATE_DEFS` / `setState`）

全部状态与「它占用哪个遮罩 / 世界是否推进 / 局内按钮是否显示」写在一张表里，**所有切换统一走 `setState()`**：

| 状态 | 遮罩 | 世界推进 | 局内按钮 | 说明 |
|---|---|---|---|---|
| `menu` | `#menu` | ✗ | ✗ | 主菜单（含各子页） |
| `playing` | — | **✓** | 显示 | 对局中，唯一会推进世界的状态 |
| `paused` | `#pause` | ✗ | ✗ | 暂停（点「继续」后还要走 3 秒读秒，见 10.1） |
| `upgrade` | `#upgrade` | ✗ | ✗ | 升级三选一 / 六选 |
| `bossreward` | `#upgrade` | ✗ | ✗ | 首领奖励（与升级共用面板，切换时不收起遮罩） |
| `merchant` | `#merchant` | ✗ | ✗ | **预留**：局内商人尚未接入，遮罩缺失时静默跳过 |
| `gameover` | `#gameover` | ✗ | ✗ | 结算（阵亡与通关共用） |

- `isLive()` 是「世界是否推进」的**唯一判据**（`update()` 及各处的 `state === 'playing'` 判断都用它）。
- `STATE_TRANSITIONS` 列了允许的转移，**只用于开发期告警、不硬拦截** —— 避免某条正常流程被表漏掉后直接卡死（非法转移在控制台留一条 `[state]` 警告，切换照旧生效）。
- `setState()` 统一负责遮罩与「暂停 / 目标优先级」按钮的显隐；`statePrev` 记录上一个状态（调试面板可读）。

### 11.2 随机流（`rngWorld` / `rngCombat` / `rngFx`）

一条随机流 = 一条可复现的 `mulberry32` 序列，三条流**互不干扰**：

| 流 | 管什么 |
|---|---|
| **world** | 地图 / 障碍物 / 装饰 / 藤蔓，以及**刷怪**（位置、种类、精英词缀、首领种类、走位初始朝向） |
| **combat** | 命中判定与概率触发（点燃 / 减速 / 冻结 / 麻痹 / 分裂 / 闪避 / 格挡）、AI 技能编排、抽卡与掉落 |
| **fx** | 纯表现：粒子、屏幕抖动、闪电分叉形状、音效噪声 —— **整条跳过也不影响战斗结果** |

- **种子写进 `meta.run`**（`seed` + `rngCounts`）：对局快照带三条流各自的取用次数，读档时把流快进回同一位置 —— **同一种子复现同一张地图与同一套战斗判定**；旧快照没有种子则记 `null`，读档保持当前流（不假装可复现）。
- `reset(seed)` 可指定种子（调试 / 测试用）；不传就每局重掷。`seedRun()` 用「种子 ⊕ 常量」派生三条流，`rngRestore()` 负责快进。
- **局外养成不进这三条流**：开蛋、装备洗练、宠物词条发生在对局之外，仍用系统随机数。

### 11.3 模块边界（单文件内先立界，暂不拆文件）

`js/game.js` 顶部有一份四层清单，后续「逐步拆文件」照它搬即可：

| 层 | 职责 | 代表区块 |
|---|---|---|
| **数据 DATA** | 只定义「是什么」，不含行为 | 常量 / 敌人与首领定义 / 四条线基础数值 / 宠物技能与养成 / 进化表 / 装备与词条表 / 卡池权重 / 存档结构 / 模式表 |
| **逻辑 LOGIC** | 规则与状态推进，改数据但不画 | 状态机 / 随机流 / 对局生命周期（reset·startGame·gameOver·winRun·快照读档）/ 战斗（update*·hitEnemy·各条线）/ 养成与存档 / 输入 |
| **渲染 RENDER** | 只读世界，往 canvas 上画 | `render()` 与全部 `draw*`（含 HUD、地形缓存）；表现层自己的数据（粒子 / petFx / 伤害数字 / 抖动）由渲染层自行推进 |
| **UI VIEW** | DOM 与交互 | 主菜单各页渲染 / 局内面板与遮罩 / 事件绑定 / 开发者面板 |

**可验证的不变量**（回归台里有断言，不是风格建议）：

- **渲染层只读世界**：连跑多次 `render()` 后，`squad / soldiers / enemies / bullets / squadHp / gameTime / wave / stats…` 的 JSON 快照逐字节不变；
- **渲染层不消耗 world / combat 随机流**（表现自己的随机走 `fxRng`）—— 所以画面设置、帧率、是否精简特效都不会影响同一局的结果；
- UI 层只改 DOM 与发起动作；逻辑层不碰 DOM（唯一例外是状态机的遮罩显隐）。

**联机同步层（V1.37）**：房主权威 + 客机回放那一套（`netConnect` / `netSend` / `netOn` / `netSnapshot` / `netApplySnap` / `netGuestTick`）**只做两件事**：把世界读成快照发出去、把收到的快照灌回世界 —— 它**不参与任何判定**。客机侧「灌快照 + `render()`」之所以安全，正是靠上面「渲染层只读世界」这条不变量（见 2.7）。
