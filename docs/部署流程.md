# 上线流程（Vercel + Supabase）

> 本文是《福瑞快打》Web 版的**部署运行手册**。面向操作者，写清每一步做什么、为什么、出问题怎么查。
> 协作约定与文档同步要求见根目录 [AGENTS.md](../AGENTS.md)；实现细节见 [需求方案.md](需求方案.md)。

## 1. 架构总览

```
浏览器（静态前端）
   │  index.html / style.css / themes.css / js/game.js / assets
   │  fetch('/api/users')         账号：注册 / 登录校验 / 存档
   │  fetch('/api/leaderboard')   排行榜：读榜 / 提交成绩
   │  WebSocket → Supabase Realtime（订阅 scores 变更，失败降级为 8 秒轮询）
   ▼
Vercel Serverless Function    api/users.js · api/leaderboard.js（Node 运行时，service 密钥只在这里）
   │  PostgREST /rest/v1/users · /rest/v1/scores · /rest/v1/rpc/submit_score
   ▼
Supabase Postgres             public.users（RLS、anon 权限已收回）
                              public.scores（RLS，anon 只读，已加入 Realtime 发布）
```

三条关键约束：

- **前端不直连数据库写**。`users` 表对 publishable / anon 权限已全部收回，账号读写只能过 `/api/users`；`scores` 表只对 anon 开放 `SELECT`（Realtime 订阅与榜单读取所必需，榜单本身就是公开数据），成绩提交只能过 `/api/leaderboard`。
- **service 密钥只存在于 Vercel 环境变量**，绝不下发前端、绝不进仓库。下发给前端的只有 publishable key，且只在排行榜的 Realtime 连接信息里。
- **本地开发与线上解耦**：`node server.js` 落盘 `data/users.json` 与 `data/scores.json`；线上写 Supabase。两者的 `/api/users`、`/api/leaderboard` 契约完全一致，前端 `js/game.js` 不感知差异。本地没有 Realtime，`realtime` 固定为 `null`，前端自动走轮询。

## 2. 首次上线

### 2.1 Supabase 侧

1. 在 https://supabase.com/dashboard 新建项目，记下 **project ref**（项目 URL 里的子域名：`https://<project-ref>.supabase.co`）。
2. 按顺序执行 `supabase/migrations/` 下的建表脚本：
   - [0001_users.sql](../supabase/migrations/0001_users.sql)：`users` 表（账号存档）+ RLS
   - [0002_leaderboard.sql](../supabase/migrations/0002_leaderboard.sql)：`scores` 表（排行榜）、`submit_score` 函数、Realtime 发布
   - [0003_password_hash.sql](../supabase/migrations/0003_password_hash.sql)：`password_hash` 列（密码由明文改为哈希）
   - [0004_submit_score_guard.sql](../supabase/migrations/0004_submit_score_guard.sql)：`submit_score` 改为带合理性校验的三参数版本
3. 取三个值备用：
   - **Project URL**（形如 `https://<project-ref>.supabase.co`）
   - **Secret / service_role key**：Project Settings → API Keys（仅服务端）
   - **Publishable key**（或旧版 anon key）：同一页（可公开，前端用于 Realtime）

> 建完表后安全顾问会出现一条 INFO 级 `rls_enabled_no_policy`，这是**预期状态**：RLS 开启 + 零策略 = 对 anon 全拒绝，只有绕过 RLS 的 service 密钥能访问。不要为了消掉这条提示而添加策略，那会打开直连读写。`scores` 表则显式带一条 `SELECT` 策略，同为设计预期。

**执行 SQL 的两种办法**

| 办法 | 做法 | 适用 |
|---|---|---|
| SQL Editor / MCP | 控制台粘贴执行；或本地挂载官方 `@supabase/mcp-server-supabase` 后用它的 `apply_migration` | 已配好访问令牌时最省事 |
| Management API 直连 | 用 `sbp_` 账号令牌直接打 `POST https://api.supabase.com/v1/projects/<ref>/database/query`（body `{"query": "<SQL>"}`，头 `Authorization: Bearer <sbp_...>`） | IDE 里的 Supabase 集成要求 OAuth 授权、而浏览器授权拉不起来时，用这条兜底 |

> 注意：Management API 的 query 接口**只返回最后一条语句的结果**，一次提交多条 `select` 时前面几条的结果会被丢弃；需要看结果就拆成单条查，或用 `json_build_object(...)` 包成一条。

### 2.2 Vercel 侧

1. 把仓库连到 Vercel：Dashboard → Add New → Project → 选 GitHub 仓库。
2. 构建设置：
   - Framework Preset：**Other**
   - Build Command / Output Directory / Root Directory：**全部留空**
   - Install Command 留空即可，由仓库里的 [vercel.json](../vercel.json) 接管（`npm install --omit=dev`，避免构建阶段下载 Electron）
3. **配环境变量**（Settings → Environment Variables，Production / Preview / Development 三项都勾）：

   | 变量名 | 值 | 用途 |
   |---|---|---|
   | `SUPABASE_URL` | `https://<project-ref>.supabase.co` | 两个接口都要 |
   | `SUPABASE_SERVICE_ROLE_KEY` | secret / service_role key | 两个接口都要，仅服务端 |
   | `SUPABASE_ANON_KEY` | publishable / anon key | 排行榜下发给前端的 Realtime 连接信息；**不配也能跑**，只是排行榜降级为轮询 |
   | `SESSION_SECRET` | 任意长随机串（如 `openssl rand -hex 32`） | 会话令牌的签名密钥；**不配也能跑**（退化为由服务密钥派生），但显式配置更稳妥，且换密钥会一次性踢掉所有登录态 |

4. Deploy。

> **顺序很重要**：环境变量要在部署前配好。改动环境变量后**必须重新部署**才生效（Vercel 不会自动重建），做法见 3.1。

> `SUPABASE_ANON_KEY` 填 **legacy anon key**（`eyJ...` 的 JWT）或 **publishable key**（`sb_publishable_...`）都可以。本项目线上用的是 legacy anon key —— 已实测它能被 Realtime 的 `apikey` 查询参数接受（§6 第 6 条）。

> **变量名必须逐字一致**。曾经踩过的坑：只配了 `SUPABASE_URL` 与 `SUPABASE_SERVICE_ROLE_KEY` 就以为「环境变量已经加好了」，因为这两个够 `/api/users` 正常跑，缺 `SUPABASE_ANON_KEY` 完全不会报错，只是排行榜的 `realtime` 一直是 `null`。补齐变量前先按 §6 第 2 条自检。

## 3. 日常更新

```bash
git add <改动文件>
git commit -m "类型: 概要"
git push origin main
```

push 到 `main` 后 Vercel **自动构建并发布**，无需手动操作：

- push `main` → Production 部署（更新生产域名）
- 开 PR → Preview 部署（独立临时 URL）

### 3.1 只改环境变量（不改代码）时的重新部署

环境变量改动**不会**触发重建，必须手动重新部署一次才生效。用 Vercel MCP 可以全程不开浏览器完成（无需改代码、无需空提交）：

```
teamId   = team_n99Q6CfJWjFWfRZAnb87wHnA
项目 ID  = prj_rub6SXxTrQJhpaL34CxujzKTmDf0      idOrName = free-quick-strike
```

| 目的 | MCP 工具 | 关键参数 |
|---|---|---|
| 查现有变量 | `filter_project_envs` | `{ idOrName, teamId }` |
| 新增变量 | `create_project_env` | `{ idOrName, teamId, requestBody: { key, value, type: 'encrypted', target: ['production','preview','development'] } }` |
| 触发重新部署 | `create_deployment` | `{ idOrName, teamId, requestBody: { name, deploymentId, target: 'production' } }` |
| 确认部署完成 | `get_project` | `{ idOrName, teamId }` → 看 `latestDeployment.readyState === 'READY'` |

`deploymentId` 取自 `get_project` 的 `latestDeployment.id`。这样触发的重新部署是**秒级**的（`source: "redeploy"`，复用已有构建产物），比 push 一个空提交干净。

几个容易踩的点：

- `create_deployment` 的 `requestBody.target` 必须显式写 `production`，漏了会生成 Preview 部署、生产域名不更新。
- `create_project_env` 的 `target` 要写全三个环境；只勾 Preview 的话生产函数读不到。
- `filter_project_envs` 返回的 `value` 是加密串，**看不到明文**——用来核对「有没有这个变量、勾了哪些环境」够用，核对具体值要回 Vercel 控制台。
- MCP 报 `Invalid arguments ... expected string, received undefined`，是 IDE 缓存的工具描述与服务器实际签名不一致，按上表的参数名传即可（例如 `get_project` 用 `idOrName` 而不是 `projectId`）。
- `teamId` 传 ID 或 slug（`leonbnbnbs-projects`）都行。

改完照 §6 验证清单复核一遍。

## 4. 地址与访问控制

| 类型 | 例子 | 匿名可访问 |
|---|---|---|
| **生产域名** | `https://free-quick-strike.vercel.app/` | ✅ 分享给别人用这个 |
| 分支别名 | `free-quick-strike-git-main-<scope>.vercel.app` | 视保护策略 |
| 部署专属 URL（带哈希） | `free-quick-strike-<hash>-<scope>.vercel.app` | ❌ 默认被 Vercel Authentication 拦 |

带哈希的部署 URL 默认需要登录 Vercel 才能打开。要临时分享给未登录的人，用 Vercel MCP 的 `get_access_to_vercel_url` 生成带 `_vercel_share` 参数的链接（**23 小时过期，别公开传播**）。

## 5. 回滚

Vercel → 项目 → Deployments → 找到上一个正常版本 → **Promote to Production**。秒级回滚，不需要重新构建。

## 6. 验证清单

每次上线后建议核对：

1. `GET https://<生产域名>/api/users` → **200** 且返回 `{"ok":true,"api":"users"}`（返回 404 说明 `api/users.js` 没部署上；返回 500 看下一节。这条只是探活，不再返回账号列表）
2. `GET https://<生产域名>/api/leaderboard` → **200** 且返回 `{"ok":true,"top":[...],"realtime":{...}}`（`realtime` 为 `null` 说明没配 `SUPABASE_ANON_KEY`，排行榜会走轮询）。
   注意 `realtime` 非 `null` 只说明接口把连接信息**下发**了，不代表前端一定连得上，两者是否真的连通以第 6 条为准。
3. **鉴权抽查**（应全部被拒绝）：
   - `GET /api/users?username=<任意账号>` 不带令牌 → **401**
   - `PATCH /api/users`（body 写别人的用户名）不带令牌 → **401**
   - `POST /api/leaderboard` 不带令牌 → **401**
   - `DELETE /api/users?username=<任意账号>` 不带令牌 → **401**
4. 浏览器打开生产域名 → 能正常注册 / 登录；**用错误密码必须登录失败**；登录后 `localStorage` 里应同时有 `fury_current_user` 与 `fury_token`
5. 注册一个测试账号后，`localStorage` 里**不应**出现 `fury_users`（出现了说明前端降级到本地存档，即 `/api/users` 不可用）
6. 打开排行榜页 → 底部显示「实时同步中」（显示「每 8 秒刷新一次」说明 Realtime 没连上，看下一节）；玩一局或改一次最佳波次后刷新榜单，成绩应更新。
   想不开浏览器先验一遍：用 Node 的全局 `WebSocket` 连 `<realtime.url>?apikey=<key>&vsn=1.0.0`（本地需配代理 + `NODE_OPTIONS=--use-env-proxy`），发 `phx_join` 订阅 `public.scores`，应收到 `{"event":"phx_reply","payload":{"status":"ok",...}}`。这一步能区分「key 本身不被 Realtime 接受」和「前端连接代码有问题」。
7. 数据库侧确认：`select username, best_wave from public.scores order by best_wave desc;` 能查到成绩；`select username, password, password_hash from public.users;` 里 **`password` 应为空、`password_hash` 以 `pbkdf2$` 开头**
8. 线上控制台无报错

## 7. 故障排查

### `/api/users` 返回 500，错误是「缺少 SUPABASE_URL / SUPABASE_SERVICE_ROLE_KEY」

环境变量没配、名字写错，或**配了但没重新部署**。核对变量名大小写，然后 Redeploy。

### `fetch failed` / 连接不上 Supabase

本地开发时的 `supabase.com` 域名在部分网络下会被阻断（控制台、文档 API 都在这个域名下），表现为 `ECONNRESET`。**线上不受影响**（Vercel 服务器不在墙内，且项目域名 `*.supabase.co` 通常可达）。
需要本地连 Supabase 时：开启系统代理，并让 Node 走代理：

```json
"env": {
  "HTTP_PROXY": "http://127.0.0.1:7890",
  "HTTPS_PROXY": "http://127.0.0.1:7890",
  "NODE_OPTIONS": "--use-env-proxy"
}
```

Node 的 `fetch` 默认不读 `HTTP_PROXY`，必须加 `NODE_OPTIONS=--use-env-proxy`（Node 24+ 原生支持）。

### 构建阶段卡在下载 Electron / 单文件超 100MB

检查 [vercel.json](../vercel.json) 的 `installCommand` 是否为 `npm install --omit=dev`，以及 [.vercelignore](../.vercelignore) 是否排除了 `electron/`、`dist/`、`node_modules/`。

### 存档写了但换设备看不到

确认第 6 节第 4 条——如果 `localStorage` 里有 `fury_users`，说明前端走的是本地降级而非云端。

### 排行榜一直显示「每 8 秒刷新一次」而不是「实时同步中」

Realtime 没连上，按顺序查：

1. **没配 `SUPABASE_ANON_KEY`**：`GET /api/leaderboard` 的 `realtime` 字段是不是 `null`。是的话补变量并重新部署（改环境变量不会自动重建，做法见 3.1）。
   核对变量时用 Vercel MCP 的 `filter_project_envs` 一眼就能看出「变量在不在、勾了哪些环境」，比逐个翻控制台快。**真实踩过的坑**：`SUPABASE_URL` 和 `SUPABASE_SERVICE_ROLE_KEY` 配好后 `/api/users` 一切正常，很容易误以为「环境变量都配好了」，而 `SUPABASE_ANON_KEY` 其实压根没建。
2. **`scores` 没进 Realtime 发布**：`select tablename from pg_publication_tables where pubname = 'supabase_realtime';` 应含 `scores`。缺了就重跑 `0002_leaderboard.sql`。
3. **anon 没有 `SELECT` 权限**：Realtime 的 `postgres_changes` 会按 RLS 与表权限过滤，`scores` 上 anon 必须至少有 `SELECT`。
4. 浏览器控制台看 WebSocket 是否被拦（公司网络 / 插件屏蔽 `wss://`）。这种情况前端会自动转轮询，功能不受影响。

> 订阅失败本身不算故障：轮询兜底会保证榜单持续刷新，只是延迟 8 秒。

### 登录一直提示「用户名或密码错误」，但密码没记错

`0003_password_hash.sql` 没执行时，`api/users.js` 查询 `password_hash` 列会报错（表现为接口 500），而如果只跑了 0001 又用老版本部署，则老账号仍是明文、能登录。核对：`select column_name from information_schema.columns where table_name = 'users';` 应含 `password_hash`。

### 旧版本前端（已加载的页面）报 400「整表覆盖已停用」

新的 `/api/users` 不再接受整表覆盖。让用户刷新页面拿新前端即可。

### 升级后所有人都被踢回登录页 / 提示「登录已失效」

v1.7 引入了会话令牌，旧的登录态（只有 `fury_current_user`、没有 `fury_token`）会失效一次，**重新登录即可**。以下情况也会导致同一现象，属预期：

- 改了 `SESSION_SECRET` → 所有已签发的令牌签名校验失败；
- 账号改过密码 → 该账号的令牌里密码版本对不上（这是刻意设计，避免改密后旧令牌继续可用）；
- 令牌超过 30 天有效期。

### 排行榜提交被拒（「成绩与对局时长不符」）

这是服务端合理性校验：要求 `波次 ≤ 时长 ÷ 2 + 30`。出现这条说明客户端上报的时长明显低于该波次所需时间。正常游玩不会触发；如果确实出现了，检查 `gameOver` 上报的 `gameTime` 是否被改动。

### 首页出现「存档暂未同步到云端」提示

说明 `PATCH /api/users` 连续失败三次（网络抖动、接口 500、令牌失效）。存档已写在本机镜像 `localStorage.fury_meta_<账号>` 里，下次登录若本机镜像比云端新会询问是否覆盖云端。令牌失效的情况会直接跳回登录页，不会只显示这条提示。
